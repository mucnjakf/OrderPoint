# OrderPoint

Order management system for a bar: customers order from their phones via QR code, bartenders fulfil orders in real time, and the owner manages everything in an admin web app. The **API**, the **Admin web app**, the **bar app**, the **Bartender app** (bartenders take orders at the tables and the counter), the **Register app** (the till: sales and payments) and the **customer app** all exist.

## Ground rules

- **Never run `git commit`, `git push`, `git merge`, `git rebase`, `git reset`, `git stash` or `gh pr create`.** Leave every change uncommitted in the working tree. When a task is done, summarise the changed files and suggest a commit message; the owner reviews and commits himself. These rules are also enforced in `.claude/settings.json`.
- **Follow the existing patterns exactly.** Before writing a new file, open the closest existing equivalent (e.g. `Item*` when adding a new entity) and mirror its structure, naming, formatting and level of detail. Do not introduce new libraries, folders, abstractions or architectural styles without asking first.
- Do not add NuGet packages or upgrade versions without asking.
- If a request is ambiguous or would require breaking an existing convention, ask before implementing.
- For anything larger than a small change, propose a plan (files to add or change, per layer) and wait for approval before editing.
- **Keep visibility as low as possible.** Every type and member gets the narrowest access modifier that compiles (`private` > `internal` > `public`). Only make something `public` when another project or a public type genuinely needs it.
- Prefer readability: clear names, early returns, no magic numbers or strings (use `const` and `nameof`).

## Tech stack

.NET 10, C# (latest), Aspire 13 for local orchestration, PostgreSQL via EF Core (Npgsql), Azure Blob Storage for images (Azurite emulator locally), Redis behind HybridCache for read caching, Minimal API, MediatR 14 (CQRS), FluentValidation 12, Scalar (API docs), OpenTelemetry. Admin web is Blazor Web App with Interactive Server render mode and MudBlazor 9; QRCoder draws the tables' QR codes.

## Commands

Run from the repo root.

```bash
dotnet build app/OrderPoint.slnx -c Release            # verify every change with this
dotnet ef migrations add <Name> \
  --project app/api/OrderPoint.Infrastructure \
  --startup-project app/api/OrderPoint.Api \
  --output-dir EfCore/Migrations \
  --configuration Release
```

- **The owner keeps the app running** (`aspire run --project app/host/OrderPoint.AppHost`) and verifies changes himself. Never start, stop or restart it; after a change, say what changed and what to check.
- While Aspire runs, the Debug outputs (`bin/Debug`) are locked, so build and run `dotnet ef` with `-c Release` / `--configuration Release`. MSB3021/MSB3027 "file is being used by another process" errors mean a Debug build hit the lock, not a compile error.
- Migrations are applied automatically on API startup (`app.ApplyMigrations()`); do not run `dotnet ef database update`.
- Migration names describe the change as `<Verb>_<What>`: `Add_Item`, `Add_ImageUrl_To_Category`, `Add_Category_Description_And_Status`, `Remove_ShortDescription_From_Item`, `Restrict_Category_Delete`.
- There is no test project yet. Do not add one unless asked.
- "Done" means the build succeeds with no warnings. The AppHost suppresses `ASPIRE010` on purpose (DCP and the dashboard come from NuGet, not the Aspire CLI bundle).
- Secrets live in user secrets, not appsettings. The Api needs `MediatR:LicenseKey`, `Jwt:SigningKey` (at least 32 characters; the API refuses to start without it) and `Admin:Email` + `Admin:Password` (the seeded admin). `appsettings.json` lists these keys with empty values. The Admin's user secrets hold the optional `CustomerApp:PublicUrl`.
- Phones reach the bar, Bartender and customer apps through the Microsoft dev tunnel `orderpoint`, the AppHost's `tunnel` resource (package `Aspire.Hosting.DevTunnels`: `AddDevTunnel("tunnel", "orderpoint", ...)` in `DevTunnelRegion.WestEurope`, `WithAnonymousAccess`, the three apps' `https` endpoints, `WithExplicitStart`, so the apps are public only while the owner starts it in the dashboard; the devtunnel CLI is signed in with GitHub). It serves `https://orderpoint-7034.euw.devtunnels.ms`, `https://orderpoint-7036.euw.devtunnels.ms` and `https://orderpoint-7038.euw.devtunnels.ms`. Only the apps' pages go through it (they call the API from the server), images included, because the apps serve them under `/images` (see Images).
- Running the app needs Docker (Aspire starts Postgres on port 59286 and the Azurite blob endpoint on port 59287, both as persistent containers with data volumes; the blob port is fixed because image URLs are stored with it). The design-time `ApplicationDbContextFactory` points at `localhost:5432`; that is fine for `migrations add`, which does not connect.

## Backend conventions

### Domain (`OrderPoint.Domain`)

- Entities are `sealed`, inherit `Entity` (`Id`, `CreatedAtUtc`, `UpdatedAtUtc`), have `private set` properties and a private constructor.
- Creation goes through `public static Result<T> Create(...)` (failures: `Result.Failure<T>(...)`); changes through `public Result Update(...)` (failures: `Result.Failure(...)`). Both validate invariants instead of throwing. `Update` sets `UpdatedAtUtc = DateTimeOffset.UtcNow`.
- IDs are `Guid.CreateVersion7()`, timestamps are `DateTimeOffset.UtcNow`.
- Navigation collections: `private readonly List<T> _items = []` exposed as `IReadOnlyList<T>`.
- Errors live in `Errors/<Entity>Errors.cs` as `static readonly Error` fields built with `Error.NotFound/Validation/Conflict/Unauthorized/Forbidden/Failure` (401/403 are used by `AuthErrors` only), code format `"<Entity>.<Reason>"`. Errors used only inside Domain are `internal`, errors used by handlers are `public`. (`Error.RequestValidation` is reserved for the API's FluentValidation exception handler.)
- Sort options are enums in `Sorting/<Entity>SortBy.cs` (`NameAsc`, `NameDesc`, ..., `CreatedAtUtcDesc`). Other enums go in `Enumerations/`.

### Application (`OrderPoint.Application`)

- One file per use case holding both the message and its handler:
  - `Commands/<Feature>/<Action><Entity>Command.cs`: `public sealed record XCommand(...) : ICommand` or `ICommand<TDto>`, plus `internal sealed class XCommandHandler(...) : ICommandHandler<...>`.
  - `Queries/<Feature>/<Get...>Query.cs`: `public sealed record XQuery(...) : IQuery<TDto>`, plus `internal sealed class XQueryHandler`.
- Use the project's own `ICommand`/`IQuery`/`ICommandHandler`/`IQueryHandler` interfaces from `Mediator/` (all `internal`), never MediatR's `IRequest` directly.
- Handlers return `Result`/`Result<T>`, never throw for business failures. Typical flow: load → `Result.Failure(XErrors.NotFound)` if null → check related entities exist → call domain `Create`/`Update` → propagate failure → repository → `unitOfWork.SaveChangesAsync`.
- Create handlers that return a DTO with navigation data reload the entity after saving (`itemRepository.GetAsync(id)`, which includes `Category`) and map that. If nothing needs loading, map directly (a new category has `itemsCount: 0`).
- Uniqueness rules (e.g. bartender email) are checked in the handler before the domain `Create`/`Update` with `repository.ExistsBy<Field>Async(value)` (e.g. `ExistsByEmailAsync`) and return a `Conflict` error; on update the check only runs when the value changed. A unique index in the EF configuration backs them up. Values are stored as entered (no trimming or lower-casing).
- In the Admin, orders are read-only except for declining an open order (below). The customer app (anonymous) reads `GET api/menu` (`GetMenuQuery`, `Queries/Menu/`: `MenuCategoryDto` with `MenuItemDto`s, only active categories in display order with their active items by name, categories without active items left out; `ICategoryRepository.GetByStatusAsync` includes the items; cached under `menu`), places orders with `POST api/orders` (the validator limits anonymous orders: at most 50 lines, each item once and 1 to 20 pieces, table code up to 10 letters, digits or hyphens) and follows them with `GET api/orders/{id}/tracking` (`GetOrderTrackingQuery` → `OrderTrackingDto`: the order without bartender details; the unguessable id is the permission; cached like `GetOrderQuery`), and can cancel it while it is still Pending with `PUT api/orders/{id}/cancel` (anonymous too, `CancelOrderCommand` → `Order.Cancel()`: status `Cancelled`, `CancelledAtUtc`). Status changes belong to the bar app and live in the domain: `Order.Accept/Decline/Activate/Complete(bartenderId)` set the status, its `<Status>AtUtc` and `UpdatedAtUtc`. Pending → Accepted (claims the order: sets `BartenderId`) → Active → Completed; Declined from Pending (any bartender, who is recorded as `BartenderId`) or from Accepted (only its bartender); declining always takes a reason for the guest (`Order.DeclineReason`, at most 200 characters, `Order.DeclineReasonIsRequired` when empty). Anything else is `Order.InvalidStatusTransition`, and acting on another bartender's order is `Order.AssignedToAnotherBartender` (both 409). There is no concurrency token (none of the entities has one). Each transition has its own command (`AcceptOrderCommand`, `DeclineOrderCommand`, `ActivateOrderCommand`, `CompleteOrderCommand`, with `Id` and `BartenderId`; each first loads the bartender: `AuthErrors.AccountDeleted` (403) if missing, `AuthErrors.AccountInactive` (403) if inactive, because a deleted or deactivated bartender's access token stays valid for up to 15 minutes; the bar app's `OrderDetails` then ends the session on either, so the login form shows) and endpoint (`PUT api/orders/{id}/accept|decline|activate|complete`, no body except decline's `{ reason }`, `NoContent`). Two more transitions keep orders from getting stuck: `Order.Release()` (Accepted or Active back to Pending, without bartender, accepted and started times cleared) runs for every open order of a bartender who is deactivated (`UpdateBartenderCommand` and `ChangeBartendersStatusCommand`, through `IOrderRepository.GetOpenByBartendersAsync`), so another bartender picks it up; `Order.DeclineByAdmin(reason)` lets the admin decline any Pending, Accepted or Active order (`DeclineOrderAsAdminCommand`; the decline endpoint is `AdminOrBartender` and picks the command by the caller's role; the bartender, if any, stays recorded). Order lines (`OrderItem`) copy the item's `Name`, `ImageUrl` and price (`UnitPrice`) when the order is placed, so later item changes do not rewrite history (`UpdateItemImageCommand` and `DeleteItemImageCommand` keep the old blob while `IOrderRepository.ExistsByImageUrlAsync` finds a line showing it; the dashboard's and My day's top items still group by item and show its current name); the order total is calculated in the mapper, not stored.
- Items have their own `ItemStatus` (Active/Inactive), but an item in an inactive category counts as inactive too: `Item.IsAvailable` (needs `Category` loaded) is true only when both are Active, and `Order.Create` rejects unavailable items with `OrderErrors.ItemIsUnavailable` (409). Deactivating a category never changes its items' own statuses. The items `status` filter uses the same effective rule (`FilterItems`), and the Admin shows it via `ItemDto.IsActive` (chips, greyscale images); only the edit form shows the item's own status (item details shows an "Inactive" chip next to an inactive category instead).
- **Tables and the floor plan:** `Area` (unique `Name`, a `Columns` × `Rows` grid of cells, `DisplayOrder` for the tabs, new areas at the end like categories), `Table` (unique `Code` of capital letters, digits and hyphens, up to 10, the code in its QR code; `Seats`, `Status` Active/Inactive, `Shape` Rectangle/Round, `X`/`Y`/`Width`/`Height` in cells) and `Fixture` (`BarCounter`, `Entrance` or `Wall`, optional `Label`, the same placement). Placement must lie inside the area (`Area.Contains`; `Table.OutsideArea`/`Fixture.OutsideArea`, 400); overlaps are left to the editor. `Area.Update` (needs tables and fixtures loaded) refuses a grid too small for its contents (`Area.TooSmallForContents`). An area with tables can't be deleted (`Area.CannotDeleteAreaWithTables`; its fixtures are deleted with it), a table with orders neither (`Table.CannotDeleteTableWithOrders`; deactivate it). Names and codes are unique (`NameAlreadyExists`, `CodeAlreadyExists`, checked in the handler, backed by unique indexes). `GET api/floor-plan` (`GetFloorPlanQuery`, AdminOrBartender) returns every area in tab order with its tables (by code, numbers compared as numbers: T2 before T10, `AreaMapper` with `CompareOptions.NumericOrdering`) and fixtures in one response; `PUT api/tables/{id}/position` and `PUT api/fixtures/{id}/position` (`MoveTableCommand`/`MoveFixtureCommand`, `{ areaId, x, y, width, height }`, also into another area; rotating swaps width and height) are what a drag sends, the other `PUT`s change the rest. Placing an order looks the table up by code (`ITableRepository.GetByCodeAsync`): `Table.NotFound` (404) or `Table.IsInactive` (409); `Order.TableId` links it and `Order.TableCode` keeps the code it was placed with, so renaming a table doesn't rewrite past orders. `GET api/orders` filters by `tableId` (and by `takenByBartenderId`, for the Bartender app) too. The customer app checks a scanned code with anonymous `GET api/tables/by-code/{code}` (`GetTableByCodeQuery` → `GuestTableDto(Code, AreaName, Status)`). The migration `Add_Areas_Tables_And_Fixtures` created the area "Inside" and a table for every code orders had used, six to a row.
- **Payments:** every order is paid when it is placed. The payment lives on the order as plain columns (one payment per order, the amount is the total): `PaymentStatus` (`Unpaid`, `Paid`, `RefundDue` = cash to hand back at the register, `Refunded`), `PaymentMethod?` (`Cash`, `Card`), `PaidAtUtc`, `RefundedAtUtc`. Guests pay by card in the customer app: `POST api/orders` takes `card { number, expiry, cvc }`, and `CreateOrderCommand` charges it through `Payments/IPaymentProvider` before saving (a declined card is `Payment.CardDeclined`, 400, and leaves no order), then calls `Order.PayByCard()` (`Payment.AlreadyPaid`, 409, if it isn't unpaid). Payments are simulated: Infrastructure `Payments/SimulatedPaymentProvider` approves every card except `4000 0000 0000 0002`; card details are never stored or logged (`CardDetails.ToString` prints no digits). `Order.Decline`, `DeclineByAdmin`, `Cancel` and `Withdraw` refund a paid order themselves: a guest's card from the customer app at once (`Refunded`, simulated), anything the register took (cash, or a card on the bar's terminal; `PaidByBartenderId` set) later (`RefundDue`, handed back at the register). The migration `Add_Payment_To_Order` marked the orders placed before as paid by card when placed (declined and cancelled ones as refunded). **The register** (Bartender policy, the Register app): `POST api/orders/register` (`CreateRegisterOrderCommand`, `Order.CreateAtRegister`: source `Register`, at the counter with an optional `CustomerName`, `TakenByBartenderId` = the bartender) sells and pays in one step and returns the `OrderDto` for the receipt; `PUT api/orders/{id}/pay` with `{ method, cashReceived }` (`PayOrderCommand`) pays a Bartender-app order. Both go through `Order.PayAtRegister(method, cashReceived, bartenderId)`: `Cash` needs `cashReceived` of at least the total (`Payment.NotEnoughCash`, 400; the validator also caps it at `PayOrderEndpoint.MaxCashReceived` 1000), `Card` is only recorded (the bar's terminal charged it) and takes no `cashReceived`; `Payment.AlreadyPaid` and `Payment.NothingToPay` (declined or cancelled) are 409. It records `PaidByBartenderId` (`OrderDto.PaidByBartender`) and `CashReceived` (precision 10,2, for the change on the receipt). `PUT api/orders/{id}/refund` (`CompleteRefundCommand`, `Order.CompleteRefund`; `Payment.NoRefundDue` 409) marks a `RefundDue` order `Refunded` once the money is handed back. `GET api/orders` filters by `payment` (`OrderPaymentFilter`: `ToPay` = unpaid and neither declined nor cancelled, `NothingToPay` = declined or cancelled before it was paid, `Paid`, `RefundDue`, `Refunded`; the register's "To pay" and "Refunds due", the Admin's Payment filter). `GET api/payments` (`GetPaymentsQuery`, `Queries/Payments/`, AdminOrBartender, tag Payments, cached under `orders` with the viewer's business date in the key) lists the orders that have a payment (`PaidAtUtc` set: paid, refund due or refunded) as `PaginationDto<OrderDto>` through `IOrderRepository.GetPaymentsPaginatedAsync`: search like orders, an optional `period` (`DashboardPeriod` by `PaidAtUtc`, from the business day start in `timeZone`, which is then required; without it every payment), `channel` (`PaymentChannel`: `Cash`, `CardAtRegister`, `CardOnline` = card without `PaidByBartenderId`), `paidByBartenderId`, `paymentStatus` (not `Unpaid`) and `PaymentSortBy` (`PaidAtUtc`, `Number`, `Total`, each Asc/Desc; default `PaidAtUtcDesc`). `GET api/register/day?timeZone=` (`GetRegisterDayQuery`, `IDashboardRepository.GetRegisterDayAsync`, not cached, tag Register) returns `RegisterDayDto(CashTotal, CardTotal, OnlineCardTotal, PaymentsCount, RefundsDueTotal, RefundsDueCount, Bartenders)` for the business day: payments still with the bar (`Paid` or `RefundDue`, since that money is still in the till), the guests' card payments, every refund due from any day, and `RegisterBartenderDto` per bartender who took payments, the most first. `Order.Total` is a computed property (not mapped) for these checks; the DTO total still comes from the mapper. Pay and refund are order-notifying (`ChangedOrders`), so the other apps update live. Deleting a bartender is also blocked by the payments they took. The migration is `Add_Register_Payment_To_Order`.
- **Where an order comes from:** `Order.Source` (`OrderSource`: `Guest` from the customer app, `Bartender` from the Bartender app, `Register`). A bartender takes an order with `POST api/orders/bartender` (Bartender policy, `CreateBartenderOrderCommand`, the bartender checks of the order commands, `Order.CreateByBartender`, the same item limits as a guest's order): it goes to the bar like any other (`Pending`) but is **unpaid** until the guest pays at the register, and `TakenByBartenderId` (`OrderDto.TakenByBartender`) records who entered it. Without a `tableCode` it is a **counter order**: `TableId` and `TableCode` are null and `CustomerName` (optional, 30 characters, kept only for counter orders) says whom to call. Everywhere an order shows its place, the shared `OrderDto.GetPlaceText()` (`OrderPoint.Shared/Extensions/OrderDtoExtensions`) gives "Table T7", "Counter · Ana" or "Counter" (the Admin's order details row is "Place"). The bartender who took a pending order can take it back with `PUT api/orders/{id}/withdraw` (`WithdrawOrderCommand`, `Order.Withdraw`: `Cancelled`, nothing to refund; `Order.EnteredByAnotherBartender` 409). Search matches the customer name too; the tables status ignores counter orders; deleting a bartender is blocked by the orders they handled or entered (`ExistsByBartender(s)Async`). The migration `Add_Source_And_Counter_To_Order` marked earlier orders as `Guest`.
- **Table requests:** a guest calls a bartender (e.g. to order in person; there is no bill, since guests pay when ordering, and the migration `Remove_Bill_TableRequests` deleted the old "Bill please" ones): `TableRequest` (`TableId`, `Type` CallBartender, the only type, `Status` Open/Done, `DoneAtUtc`; who did it is not stored, so deleting a bartender is never blocked). Anonymous `POST api/tables/by-code/{code}/requests` with `{ type }` (`CreateTableRequestCommand`; `Table.NotFound`, `Table.IsInactive`) returns `200` with the open request: a table has at most one open request of each type, and asking again returns it. Anonymous `GET api/tables/by-code/{code}/requests` (`GetTableRequestsByCodeQuery`) lists the table's open ones for its guests; the bar app reads every open one with `GET api/table-requests` (`GetTableRequestsQuery`, oldest first) and marks one done with `PUT api/table-requests/{id}/done` (`CompleteTableRequestCommand`; bartender checks like the order commands, `TableRequest.AlreadyDone` 409). None of it is cached. Deleting a table deletes its requests. Shared web: `TableRequestDto`, the two enums and `TableRequestTypeExtensions` ("Call bartender", `RoomService` icon).
- Categories have a `DisplayOrder`, the order of the menu in the customer app.
  - **New categories:** they go to the end (`GetMaxDisplayOrderAsync() + 1`). Deleting one leaves a gap, because only the relative order matters.
  - **Reordering:** `ReorderCategoriesCommand` (`PUT api/categories/display-order` with every category id in the new order) renumbers them 1..n. It fails with `CategoryErrors.DisplayOrderMustIncludeAllCategories` unless the list contains every category exactly once.
  - **Admin:** the Categories table has a "Display order" column and Display order ↑/↓ in its sort dropdown (the default stays Created ↓), and category details show it under the ID. Its "Reorder" button (`DataTable.ToolbarActionsContent`) opens `ReorderCategoriesDialog`, a `MudDropContainer` list (loads up to 100 categories). After each drop the dialog reorders its own list and calls `DropContainer.Refresh()`, so the drop zone's internal order can't drift from it.
- Deleting a parent that still has children is blocked in the handler with a `Conflict` error (e.g. `CategoryErrors.CannotDeleteCategoryWithItems`), backed by `DeleteBehavior.Restrict` on the foreign key.
- Bulk commands (`Change<Plural>StatusCommand`, `Delete<Plural>Command` for categories, items and bartenders) are all-or-nothing:
  - They load every id with `GetAsync(IReadOnlyList<Guid> ids)` and return the entity's `NotFound` if any is missing.
  - Blockers are checked for the whole set (`ExistsByCategoriesAsync`, `ExistsByItemsAsync`, `ExistsByBartendersAsync`), returning the single-entity `Conflict` error.
  - They call the domain `ChangeStatus(status)` (a no-op when the status is unchanged) or the repository `Delete` on each, and save once.
  - Image blobs are deleted after saving. Bartender deactivation revokes refresh tokens and releases their open orders, and bartender deletion also deletes the logins.
  - Items have two more bulk commands:
    - `ChangeItemsCategoryCommand` checks that the category exists, then calls `Item.ChangeCategory`.
    - `AdjustItemsPriceCommand` takes a `PriceAdjustmentMode` (`Set`, `ChangeByPercent`, `ChangeByAmount`) and a value. It computes each new price, rounds it to 2 decimals (away from zero) and calls `Item.ChangePrice`. If any price would not be positive, nothing is saved.
- DTOs: `public sealed record XDto(...)` in `Dtos/`. Mapping is manual via extension methods in `Dtos/Mappers/<Entity>Mapper.cs` (`ToXDto()`). No AutoMapper.
- Lists: paged lists return `PaginationDto<T>` (`Get<Plural>Query`). Unpaged lookups, such as autocomplete search, return `IReadOnlyList<T>` (`Search<Plural>Query`).
- Repository interfaces in `Repositories/` (`GetPaginatedAsync`, `SearchAsync`, `GetAsync`, `CreateAsync`, `Delete`, `ExistsAsync`...). Methods that look the entity up by its own id have no suffix (`GetAsync(Guid id)`, `GetAsync(IReadOnlyList<Guid> ids)`, `ICategoryRepository.ExistsAsync(Guid id)`). Methods filtering by anything else say what they filter by in the name, and the parameter is named after it: `IItemRepository.ExistsByCategoryAsync(Guid categoryId)` = "any item in this category", `CountByCategoryAsync(Guid categoryId)`, `IBartenderRepository.ExistsByEmailAsync(string email)`, `IOrderRepository.ExistsByItemAsync(Guid itemId)`, `CountByBartendersAsync(IReadOnlyList<Guid> bartenderIds)`. Saving goes through `IUnitOfWork`, never from a repository.
- Counts of children for a page of entities come from one grouped query that returns a dictionary (`IOrderRepository.CountByItemsAsync(itemIds)` for `GetItemsQuery`, `CountByBartendersAsync(bartenderIds)` for `GetBartendersQuery`), not from including the child collection. A single entity uses the scalar version (`CountByItemAsync(Guid itemId)`). Categories still include `Items` for their counts, which is fine while categories hold few items.
- Dashboard is the one read-model exception: `IDashboardRepository` (no entity of its own) returns DTOs straight from aggregations over orders, because loading entities to sum them would be wasteful. Each dashboard widget has its own query (`Queries/Dashboard/`) and endpoint (`api/dashboard/<widget>?period=Today|Last7Days|Last30Days&timeZone=<IANA id>`; busiest times and live take only `timeZone`) so widgets load in parallel. Periods are calendar based in the viewer's time zone, sent by the Admin and validated with the shared `MustBeValidTimeZone()` rule (`DashboardPeriodRange` computes local midnights with `LocalToUtc`/`UtcToLocal`; buckets are built from local dates, never by adding fixed lengths, so DST days stay correct): A day starts at the business day's start hour, not at midnight, so a night past midnight is one day: the AppHost's `BusinessDayStartHour` (6) reaches the API and the bar app as `BusinessDay:StartHour`, the API registers it as the singleton `Queries/Dashboard/BusinessDay` (missing = midnight, outside 0-23 stops the API), and handlers pass `businessDay.StartTime` to `DashboardPeriodRange.For` and the dashboard `CacheKeys.For` overloads (`GetLocalToday(now, timeZone, dayStart)` is the business date). Today = since the day start, Last7Days/Last30Days include today (daily buckets start at the day start), and "previous" is the same-length window right before. Revenue is what was paid: orders with `PaymentStatus.Paid`, dated by `PaidAtUtc` (`IDashboardRepository.GetPaymentsAsync` → `DashboardPaymentDto(Total, PaidAtUtc, PaymentMethod, PaidByBartenderId)`; refunded payments and refunds due drop out). The summary's revenue and average order value, the revenue trend's buckets, today's revenue and average in live, the category donut and top items (`GetPaidOrderItemsInRange`) and the leaderboard's revenue (per handling bartender) all use it; order counts include every status by order time, and service times count completed orders. `GET api/dashboard/payment-methods` (`GetPaymentMethodsQuery` → `PaymentMethodsDto(CashTotal, CashCount, CardTotal, CardCount, OnlineCardTotal, OnlineCardCount)`, cached like the other widgets) splits the period's payments into cash, card at the register and card online. Live also returns what waits at the register from any day: `ToPayCount`/`ToPayTotal` (unpaid, neither declined nor cancelled) and `RefundsDueCount`/`RefundsDueTotal`. Busiest times always cover the last 28 days and group by local weekday and hour on calendar days (`TimeSpan.Zero`), since its axes are clock hours. The bar app's "My shift" uses the same repository: `GetShiftQuery` (`Queries/Shift/`, `GET api/shift?timeZone=`, Bartender policy, not cached) returns `ShiftDto(PendingCount, MyOpenCount, CompletedCount, AverageServiceMinutes)`: every pending order, the bartender's accepted and active ones, and the ones they completed since the day start (by `CompletedAtUtc`, so an order placed before it still counts) with the dashboard's service time (placed → completed). `GetShiftDayQuery` (`GET api/shift/day?timeZone=`, same rules) returns `ShiftDayDto(Revenue, ItemsCount, Hours, TopItems)` for the orders the bartender completed since the day start: total, pieces, `ShiftHourDto(Hour, CompletedCount)` per local hour from the first hour with a completed order to the current hour, counted from the day start (22, 23, 0, 1 for a night) (quiet hours as 0; empty without completed orders), and the top 3 items (`TopItemDto`); the repository methods are `GetCompletedOrdersByBartenderAsync` and `GetCompletedItemsByBartenderAsync`.
- MediatR handlers are registered by assembly scan; no manual registration needed.

### Infrastructure (`OrderPoint.Infrastructure`)

- `ApplicationDbContext` implements `IUnitOfWork`; `DbSet`s are `internal`.
- One `IEntityTypeConfiguration<T>` per entity in `EfCore/EntityTypeConfiguration/` (table name, `ValueGeneratedNever()` on Id, `HasMaxLength`, `IsRequired`, relationships). Each property is configured as `builder` / `.Property(...)` / `...` on separate lines. Relationships use `.OnDelete(DeleteBehavior.Restrict)`. Picked up by assembly scan. Money columns (`Item.Price`, `OrderItem.UnitPrice`) use `HasPrecision(10, 2)`. The only database-generated value is `Order.Number` (`UseIdentityAlwaysColumn()` plus a unique index), the human-readable order number.
- Repositories are `internal sealed class <Entity>EfCoreRepository(ApplicationDbContext dbContext)` in `EfCore/Repositories/`, using private static `Search<X>`/`Filter<X>`/`Sort<X>` helpers for paginated queries (search is case-insensitive via `ToLower().Contains`; default sort `CreatedAtUtc` descending; unpaged search sorts by name ascending). `Sort<X>` builds an `IOrderedQueryable` and always ends with `.ThenBy(x => x.Id)` so paging is stable when sort values tie. Read-only queries (`GetPaginatedAsync`, `SearchAsync`) use `AsNoTracking()`; `GetAsync` stays tracked because commands update and delete what it returns, and it includes the navigations its DTO needs. Register in `InfrastructureModule`.

### API (`OrderPoint.Api`)

- `Program.cs` pipeline order: `ApplyMigrations` → `SeedAdminAsync` → `UseExceptionHandler` (first middleware) → `UseHttpsRedirection` → `UseCors` → `UseAuthentication` → `UseAuthorization` → endpoint, hub and docs mapping. `launchSettings.json` URLs never contain a path (Kestrel refuses them); use `launchUrl` instead.
- CORS: one policy that allows only the origins in `Cors:AllowedOrigins` (empty by default in `appsettings.json`), any header, and GET/POST/PUT/DELETE. Nothing needs CORS today (the Admin, the bar app and the customer app are Blazor Server and call the API from their servers, Scalar is same-origin); add an origin only for a client that calls the API from the browser (e.g. a WebAssembly or JS client). Never go back to `AllowAnyOrigin`.
- One endpoint per file in `Endpoints/<Feature>/<Action><Entity>Endpoint.cs`: `internal sealed class XEndpoint : IEndpoint`, discovered automatically.
- Request and response records (`internal sealed record`) are declared in the same file above the endpoint; the FluentValidation validator is a nested `internal sealed class XRequestValidator` inside the endpoint class (auto-registered). Every endpoint that takes a body or query string has a request record and a validator.
- Query-string input is bound into a request record with `[AsParameters] XRequest request`; its constructor parameters carry `[FromQuery]` (see `GetItemsEndpoint`, `SearchCategoriesEndpoint`). Paged lists validate `PageNumber > 0` and `PageSize` between 1 and 100; search text is at most 100 characters (a search that cannot match returns no results, not an error); required search text uses `NotEmpty()` (also rejects whitespace). Route values (`{id:guid}`) stay as `[FromRoute]` parameters.
- `MapEndpoint` uses route `api/<plural>`, `api/<plural>/{id:guid}`, `api/<plural>/search?searchQuery=...` (unpaged lookup), plus `.WithName("<Action><Entity>")`, `.WithTags("<Plural>")` and, for every Admin endpoint, `.RequireAuthorization(AuthorizationPolicies.Admin)` as the last call. Endpoints without `RequireAuthorization` are anonymous (auth endpoints, the customer app's `GET api/menu`, `POST api/orders`, `GET api/orders/{id}/tracking`, `PUT api/orders/{id}/cancel`, `GET api/tables/by-code/{code}` and its `requests` (`GET`, `POST`), health checks, API docs), so never forget it on a new Admin endpoint. Bar app endpoints use `AuthorizationPolicies.Bartender` (or `AdminOrBartender` when the Admin calls them too) instead and take the bartender id from the token (`user.GetUserId()`; a bartender's user id is the `Bartender.Id`).
- API documentation (Scalar at `/scalar`, document at `/openapi/v1.json`). Every endpoint and record is documented:
  - **Endpoint chain:** after `.WithTags(...)` comes `.WithSummary("Short imperative")`, then `.WithDescription("""...""")` (Markdown: what it does, the rules, and one bullet per domain error, e.g. ``- `409 Category.CannotDeleteCategoryWithItems`: the category still has items``), then `.ProducesProblem(StatusCodes.Status404NotFound)` / `409` / `401` / `403` for the errors the handler can return. 400, the auth 401/403 and 500 are added automatically.
  - **Records:** request and response records (Api) and DTOs (Application) get `/// <summary>` plus one `/// <param name="Field">` per positional parameter, all of them (a partial set warns with CS1573). Escape `<`/`>` as `&lt;`/`&gt;`. Api and Application set `GenerateDocumentationFile` (CS1591 suppressed); the OpenAPI source generator picks the comments up, including from the referenced Application project.
  - **Transformers** live in `OpenApi/`, registered by `AddApiDocumentation()` and mapped by `MapApiDocumentation()`. Never edit the generated document by hand.

    | Transformer | What it does |
    | --- | --- |
    | `DocumentInfoTransformer` | Title, the Markdown guide in `ApiGuide.cs` (authentication, envelope, pagination, errors, conventions), tag descriptions, `x-tagGroups`, the bearer scheme |
    | `SecurityTransformer` | The bearer requirement, a role note (the roles its policy allows, read from `AuthorizationOptions`), and 401/403, only on endpoints with `RequireAuthorization` |
    | `ResponsesTransformer` | 400 for endpoints with a body or query parameters; clear descriptions for the standard status codes |
    | `ProblemDetailsSchemaTransformer` | The `errors` array on `ProblemDetails` |
    | `EnumSchemaTransformer` | Enum values, names and `x-enum-varnames` |
    | `NumberSchemaTransformer` | Drops the "number or string" noise |
    | `ValidationTransformer` + `ValidationRules` | Copies unconditional FluentValidation rules (NotEmpty, lengths, comparisons, ranges, email) into body schemas and `[AsParameters]` query parameters; `When` and `Must` rules cannot be expressed in a schema, so describe them in the endpoint's `.WithDescription` |
  - **Shared 500:** `MapEndpoints` maps every endpoint in an empty group with `.ProducesProblem(500)`, which also registers the shared `ProblemDetails` schema.
- `private static async Task<Results<..., ProblemHttpResult>> HandleAsync(...)` with explicit `[FromBody]`/`[FromRoute]`/`[FromQuery]`/`[FromServices]` attributes and a `CancellationToken`.
- Flow: `await validator.ValidateAndThrowAsync(request, ct)` → build command/query → `sender.Send` → `result.IsSuccess ? TypedResults.X(...) : result.ToProblemDetails()`.
- Responses wrap payloads as `{ Data }`: create → `CreatedAtRoute` to the Get route, update/delete → `NoContent`, get → `Ok`.
- Bulk endpoints: `PUT api/<plural>/status` with `{ ids, status }` and `POST api/<plural>/delete` with `{ ids }`, both returning `NoContent`. Their validators use the shared `RuleFor(request => request.Ids).MustBeValidIds()` (`Extensions/IdsValidationExtensions.cs`: 1 to 100 ids, no empty id, no duplicates). Items also have `PUT api/items/category` with `{ ids, categoryId }` and `PUT api/items/price` with `{ ids, mode, value }`. The price value must be positive for `Set`, non-zero otherwise, and above -100 for `ChangeByPercent`.
- Errors are ProblemDetails with an `errors` array; status mapping lives in `Extensions/ResultExtensions.cs`. Exception handlers in `Exceptions/` (registered in `Program.cs`, in order): `RequestValidationExceptionHandler` (FluentValidation → 400), `BadHttpRequestExceptionHandler` (missing/unparsable parameters or malformed JSON → 400; `ThrowOnBadRequest` is on so this applies in every environment), `GlobalExceptionHandler` (logs the exception, → 500 without exposing exception details). In .NET 10 the exception middleware does not log exceptions a handler reports as handled, so any new handler for unexpected errors must log itself.

### Caching

- Reads are cached with `HybridCache` (`AddHybridCache` in `InfrastructureModule`: 5 minutes in memory, 30 minutes in Redis). The API's `builder.AddRedisDistributedCache("cache")` registers the `IDistributedCache` HybridCache uses as its second level. Redis has no data volume, so every run starts empty. `BacklogPolicy.FailFast` makes Redis calls fail at once while it is down, so reads fall back to memory and the database instead of waiting for a timeout. Its health check (`StackExchange.Redis`, shown as "Cache") reports `Degraded` through `ReportHealthCheckFailureAsDegraded`.
- **Reads:** the query handler wraps its work in `cache.GetOrCreateAsync(CacheKeys.For(query), query, Get<X>Async, tags: [CacheTags.<Feature>], cancellationToken: ...)`. The old `Handle` body lives in `private async ValueTask<TDto> Get<X>Async(query, ct)`, and `Handle` turns the DTO into the `Result` (a not-found is cached as `null` and mapped to the `NotFound` error). The DTO is cached, never `Result<T>` (not serializable). Cached: get, list and search for categories, items, bartenders and orders, payments, order tracking, the guests' menu, the floor plan, one area, table (also by code) or fixture (tag `tables`, `CacheTags.TableChanges`), and every dashboard widget except live. Not cached: live, shift, account, auth, health.
- **Keys:** `Caching/CacheKeys.For(<query>)`, one overload per query, `<feature>:<id>`, `<feature>:page:<every parameter>` and `<feature>:search:<text>`, free text always last. Dashboard keys hold the period, the time zone id and the viewer's local date, so periods move on at the day start.
- **Writes:** a command whose change shows up in cached reads implements `Mediator/ICacheInvalidatingCommand` explicitly (`IReadOnlyList<string> ICacheInvalidatingCommand.InvalidatedCacheTags => CacheTags.<X>Changes;`), and `Mediator/CacheInvalidationBehavior` (after `TelemetryBehavior`) calls `RemoveByTagAsync` once the command succeeds, with `CancellationToken.None` so a caller who left can't keep stale data. The groups in `Caching/CacheTags` follow what each DTO shows: `CategoryChanges` (categories, items, dashboard, menu), `ItemChanges` (items, categories, orders, dashboard, menu), `BartenderChanges` (bartenders, orders, dashboard), `OrderChanges` (orders, items, bartenders, dashboard). Auth, account and `ResetBartenderPasswordCommand` change nothing cached.
- **New use cases:** a new query gets a `CacheKeys.For` overload and the tag of its feature; a new command that changes something a cached DTO shows implements `ICacheInvalidatingCommand`, and a new DTO field that comes from another feature means adding that feature's changes to its group. The order status changes (bar app) use `OrderChanges`.

### Real time

- The staff hub, `Api/Hubs/OrdersHub` (`builder.Services.AddSignalR()`, `app.MapHub<OrdersHub>("hubs/orders").RequireAuthorization(AuthorizationPolicies.AdminOrBartender)`). Clients only listen; the hub has no methods. The Admin and the bar app are Blazor Server, so they connect with the .NET client from the server, which sends the bearer token as a header (no `access_token` query handling, no CORS).
- Its messages are `OrdersChanged` (`OrdersHub.OrdersChangedMethod`), `MenuChanged` (`MenuChangedMethod`) and `TablesChanged` (`TablesChangedMethod`), all without arguments: clients reload what they show.
- **Sending:** the commands that place an order or change its status (`CreateOrderCommand`, `Accept/Decline/Activate/CompleteOrderCommand`, `DeclineOrderAsAdminCommand`, `CancelOrderCommand`) implement the marker `Mediator/IOrderNotifyingCommand`. `Mediator/OrderNotificationBehavior` (registered between `TelemetryBehavior` and `CacheInvalidationBehavior`, so it runs after the cache is cleared and a reload is never stale) calls `Notifications/IOrderNotifier` once such a command succeeds. `Api/Hubs/SignalROrderNotifier` (singleton) sends to all clients and logs a warning instead of failing when sending fails, because the change is already saved.
- A new command that changes what the apps show about orders implements `IOrderNotifyingCommand` too, and its handler adds every order it changed to the scoped `Notifications/ChangedOrders` after saving (a release can change several, known only once the handler ran; `CreateOrderCommand` adds none, nobody can follow an order before it exists). The bartender commands that can deactivate (`UpdateBartenderCommand`, `ChangeBartendersStatusCommand`) are order-notifying too, because they release orders.
- **Guests:** a second hub, `Api/Hubs/OrderTrackingHub` (`app.MapHub<OrderTrackingHub>("hubs/order-tracking")`, anonymous), for the customer app. Its one method `TrackOrder(orderId)` (`TrackOrderMethod`) adds the connection to the group `order:<id>`; clients call it for every order they follow and again after a reconnect (groups are lost). `IOrderNotifier.NotifyOrdersChangedAsync(changedOrderIds)` (called by `OrderNotificationBehavior` with `ChangedOrders.OrderIds`) sends `OrdersChanged` to the staff hub and `OrderChanged` (no arguments, `OrderChangedMethod`) to the groups of the changed orders, so a guest only hears about their own orders.
- **Tables:** every area, table, fixture and table request command implements `Mediator/ITablesNotifyingCommand`; `Mediator/TablesNotificationBehavior` (right after `MenuNotificationBehavior`) calls `Notifications/ITablesNotifier`, and `Api/Hubs/SignalRTablesNotifier` sends `TablesChanged` to every connection of both hubs.
- **Menu:** every item and category command (17, including status, price, image and menu order) implements the marker `Mediator/IMenuNotifyingCommand`; `Mediator/MenuNotificationBehavior` (registered right after `OrderNotificationBehavior`, also outside `CacheInvalidationBehavior`, so a reload is never stale) calls `Notifications/IMenuNotifier` once such a command succeeds, and `Api/Hubs/SignalRMenuNotifier` (singleton, logs a warning instead of failing) sends `MenuChanged` to every connection of both hubs, since anyone may be looking at the menu. A new command that changes an item or a category implements the marker too.
- **Receiving:** `OrderPoint.Shared/Orders/Services/OrdersHubService` (scoped, one connection per circuit, package `Microsoft.AspNetCore.SignalR.Client`) connects to `<api>/hubs/orders`. WebSockets bypass the service discovery HttpClient, so the URL comes from Aspire's `services:order-point-api:https:0` (else `http:0`); the token comes from `AuthService.GetAccessTokenAsync`. The first connect and automatic reconnects retry after 0, 2, 10 and then every 30 s. It raises `OrdersChanged`, `MenuChanged` and `TablesChanged` on their messages and all three after a reconnect (messages sent while down are lost), and `StateChanged` with `State` for a connection indicator. `MainLayout` starts it after sign-in (not awaited) and stops it on sign-out; the circuit scope disposes it.
- **Admin pages:** everything that shows order data subscribes to `OrdersChanged` (and everything that shows items or categories to `MenuChanged`: `CategoriesPage` (table and top 5, selection kept), `ItemsPage` (grid and spotlight), `CategoryDetailsDialog` (its items) and `ItemDetailsDialog`, which refetches the item into `CurrentItem` because the dialog provider resets parameters) in `OnInitialized(Async)`, unsubscribes in `Dispose`, and reloads silently: `OrdersPage` (status counts + the current timeline page, filters kept), `DashboardPage` (every section; the live panel keeps its 30 s timer too), `ItemsPage` and `BartendersPage` (the current page, for the order counts; not the spotlight or team strip), `BartenderOrdersList` (`BartenderOrdersDialog`), `BartenderOrdersSummary` (the expanded bartender row's last order), `ItemDetailsDialog` (orders count and list) and `OrderDetailsDialog` (refetches the order into `CurrentOrder`, because the dialog provider resets parameters; for an open order it has a "Decline order" button on the left of the actions, which asks in `Orders/Dialogs/DeclineOrderDialog` (order summary, "This action cannot be undone. The guest sees the order as declined, with your reason.", and the shared `DeclineReasonField`: quick-pick chips from `OrderPoint.Shared/Constants/DeclineReasons` that fill the required "Reason for the guest" field, 200 characters, clearable; the dialog returns a `DeclineOrderRequest`, and a declined order shows a "Decline reason" row) and calls `PUT api/orders/{id}/decline` itself, since the dialog opens from several pages that all reload on `OrdersChanged`). Load methods take `bool isLiveUpdate = false`: a live update shows no skeleton and keeps the bulk selection (re-pointed by id at the reloaded records); on the dashboard `OnPeriodChangedAsync` sets the loading flags itself. `DataAccordion` keys its panels with `GetItemKey` (the id), so a live reload keeps an expanded row open.
- **New orders:** `NewOrdersTracker` (`OrderPoint.Shared/Orders/Services`, one per list, not DI) marks orders created after the list's previous load started as new for 10 s; the Orders timeline (`DataTimeline.IsItemNew`) and the dashboard's `RecentOrdersList` wrap them in `NewItemHighlight` (tinted background that fades over 3 s) and show a filled "New" chip (next to the status chip on tickets, instead of it in Recent orders, so the row shows "New" first and then its status). `Orders/Services/NewOrderToastService` (scoped, driven by `MainLayout`: baseline after sign-in, `CheckAsync` on every `OrdersChanged`) compares the 5 newest order numbers with the last one it saw and shows a snackbar on every page: "New order #128 · Table 4 · €23.50" (View opens `OrderDetailsDialog`) or "3 new orders" (View opens `/orders`); the action button uses `ActionVariant = Variant.Text`, because the outlined snackbars would give it a border. Both stay 5 s (`ToastVisibleMilliseconds`, so there is time to click View) and set `RequireInteraction = false`, because MudBlazor keeps a snackbar with an action open until it is clicked.
- **Changing numbers:** live numbers (status counts, KPI values, Right now values, top items and leaderboard numbers) render through `RollingNumber` (`OrderPoint.Shared/Components`, generic `Value` for the direction + formatted `Text`): when the value changes the old text slides out and the new one in, up when it grew, down when it shrank; never on first render, off under `prefers-reduced-motion`. Use it for any new number that live updates change.

### Images

- Images live in the blob container `images` and the entity stores the full public URL in `ImageUrl` (UI uses it directly). The API gets a `BlobContainerClient` from `builder.AddAzureBlobContainerClient("images")` and `app.CreateImageContainer()` makes the container publicly readable at startup.
- Phones can't reach the emulator, so the bar and customer apps serve images themselves (`OrderPoint.Shared/Images`): the AppHost passes them `Images__StorageUrl` (`http://127.0.0.1:59287/devstoreaccount1/images`, the start of every stored URL), `AddImageProxy()` puts `ImageUrlHandler` on every HTTP client through `ConfigureHttpClientDefaults` (it replaces that prefix with `/images/` in JSON responses), and `MapImageProxy()` maps `GET /images/{**path}`, which streams the blob from storage with a one-year immutable `Cache-Control` (refuses `..`). Without the setting both do nothing. The Admin and the API are unchanged; uploads and stored URLs stay as they are.
- `IImageStorage` (Application `Storage/`, implemented by Infrastructure `Storage/BlobImageStorage`): `UploadAsync(stream, contentType, folder)` stores `<folder>/<guid>` and returns the URL; `DeleteAsync(imageUrl)`. A new upload always gets a new name, so browsers never show a cached old image.
- Images are not part of create/update. Each entity with an image gets `PUT api/<plural>/{id}/image` (multipart form field `image`, `[FromForm]` request record, `.DisableAntiforgery()`) and `DELETE api/<plural>/{id}/image`, backed by `Update<Entity>ImageCommand`/`Delete<Entity>ImageCommand` and domain `SetImage(url)`/`RemoveImage()`. Replacing an image deletes the old blob after saving; deleting the entity deletes its blob. An item's old blob stays while an order line still shows it. Limits: JPEG, PNG or WebP, at most 2 MB, checked by the API validators through the shared `RuleFor(request => request.Image).MustBeValidImage()` (`Extensions/ImageValidationExtensions.cs`) and by the Admin `ImageUploadField`.
- Admin: dialogs use the shared `ImageUploadField` (upload button, optional remove, inline error) which reads the file into an `ImageFileDto`; the preview paper shows it via `ImageFileDto.ToDataUrl()`. The request carries it as `[JsonIgnore] Image` (update also `[JsonIgnore] RemoveImage`), and the page sends create/update and then the image call inside one `ApiService.ExecuteAsync` (see `CategoriesPage`).
- Categories, Items and Bartenders all have uploads (blob folders `categories/`, `items/`, `bartenders/`), and so does the admin account (`users/`, `ApplicationUser.ImageUrl`, `PUT`/`DELETE api/account/image`). Bartenders without an image show coloured initials in `BartenderAvatar` (`OrderPoint.Shared/Bartenders/Components`, used by the Admin, the Bar app and the Register; text size follows the avatar `Size`). **Every name comes with its picture, in every app:** a bartender with `BartenderAvatar` (`Size.Small` next to captions and body text: taken by, handled by, paid to, served by, the Register's per-bartender rows and payments), an order line, item or category with a thumbnail (24px with `ImageStyles.RoundedSmall` in compact lines: Bar tickets, Bartender-app order cards, the customer's Orders cards and Pay summary, the dashboard donut). Only the printed till receipt stays text. Item cards use the shared `ItemCardContent` (`OrderPoint.Shared/Items/Components`, plain-value parameters so each app keeps its own `ItemDto`; the caller wraps it in a `MudCard`; `IsDescriptionClamped="false"` shows the whole description; `Portion` and `OrdersCount` are optional (null hides them; " · " only appears between both) and `ShowsStatus="false"` hides the status chip, all three for guests), used by the Admin's `ItemsPage` grid and the bar app's `MenuItemPage`. Its top is `ItemCardImage`: the image at a fixed height, uncropped, centred over a blurred, faded copy of itself that fills the card's top area (so the background matches the image's colours), or the centred placeholder in an area of the same height. Below it the card reads like a menu: muted category (16px thumbnail and name) with the small Active/Inactive chip (20px, caption-sized) at the other end of that row, name (h6), description clamped to 2 lines, and a bottom row (`mt-auto`, so footers line up) with the price on the left and "portion · n orders" on the right. Missing images fall back to `ImageUrls.Placeholder` (`OrderPoint.Shared/Constants/ImageUrls.cs`): `Src="@(x.ImageUrl ?? ImageUrls.Placeholder)"`. Small fixed-size thumbnails use `MudImage` with `ObjectFit.Cover` so photos are cropped, not stretched; never `MudCardMedia` inside a list row (it defaults to 300px tall). Every item and category picture has soft corners from `OrderPoint.Shared/Constants/ImageStyles`: `Style="@ImageStyles.Rounded"` (the theme radius) from 32 px up, `@ImageStyles.RoundedSmall` (4px) for thumbnails up to 24 px, so they don't turn into circles; combine it with other styles (`$"{ImageStyles.Rounded} flex-shrink: 0;"`), never hand-write the radius.
- Orders have no image; `OrderAvatar` (`OrderPoint.Shared/Orders/Components`) shows `#<Number>` (h6) in a rounded grey tile (filled `MudAvatar` that stretches to the height of the text beside it, at least 72px wide so up to 4 digits line up). Every order list row uses the same layout: tile, `Spacing="3"`, "Table T11" over the time, spacer, status chip, total. The order details dialog shows the number as plain text. Orders timeline tickets are split in two by a vertical divider: on the left (45%) the header (tile, table and time, status chip), the note, and the bartender with the total at the bottom; on the right each order line with a 32px image, "2× name" and the line total. Below the note a declined ticket says "Declined: <reason>" and a cancelled one "Cancelled by the guest" (status icon, secondary text).

### Authentication

- ASP.NET Core Identity, but only its user store: `UserManager` with `UserOnlyStore` on the plain `ApplicationDbContext` (password hashing, lockout, unique email, security stamp). No `SignInManager`, `MapIdentityApi`, Identity UI, cookies, claims, external logins, 2FA or Identity roles. Tables: `Users` (Infrastructure `Identity/ApplicationUser`, fully configured in `ApplicationUserTypeConfiguration`, unused Identity columns ignored) and `RefreshTokens`.
- Two roles in `UserRole` (a column on the user): `Admin` (only seeded at startup from `Admin:Email`/`Admin:Password` when that email does not exist yet) and `Bartender`. A bartender's user has the same `Id` as the `Bartender` row; creating a bartender creates the login (temporary password, `MustChangePassword = true`), changing the email updates it, deactivating revokes refresh tokens, deleting deletes it. A forgotten password is reset by the admin (`PUT api/bartenders/{id}/password`, "Reset password" button in the bartender's expanded row): a new temporary password, `MustChangePassword = true` again, lockout lifted, refresh tokens revoked.
- Application talks to Identity only through `Identity/IIdentityService` and `Identity/ITokenService` (implemented in Infrastructure `Identity/`). The user store (`ApplicationUserStore`) runs with `AutoSaveChanges = false`, so user and token changes are saved by the handler's `IUnitOfWork` together with everything else; its `UpdateAsync` only marks the user modified, because the base store re-attaches the user, which breaks the concurrency check when one request makes several user updates before saving.
- Tokens: JWT access token (HS256, 15 minutes, claims `sub`, `email`, `role`) and a random refresh token (7 days, only its SHA-256 hash stored, replaced on every refresh). Lifetimes, issuer and audience are in `appsettings.json` (`Jwt`), the key in user secrets. `ClockSkew` is zero. `AuthTokensDto` (login, refresh, password change) carries `UserId` (a bartender's is their `Bartender.Id`), `Email` and `Role` next to the tokens.
- Endpoints (anonymous): `POST api/auth/login` (`email`, `password`, `role`), `POST api/auth/initial-password` (first login only), `POST api/auth/refresh`, `POST api/auth/logout`. The account endpoints take the user id from the token (`ClaimsPrincipal.GetUserId()`, `Extensions/ClaimsPrincipalExtensions.cs`). `PUT api/account/password` changes the password; a wrong current password is `AuthErrors.InvalidCurrentPassword` (400, not 401, so the Admin doesn't treat it as an expired session). It then revokes every refresh token and returns a new token pair, which the Admin stores with `AuthService.ReplaceTokensAsync`. `POST api/account/sign-out-everywhere` revokes every refresh token, and the Admin then calls `AuthService.EndSessionAsync`. `GET api/account` returns `AccountDto(Email, ImageUrl, FirstName, LastName, PhoneNumber)`; for a bartender `ImageUrl` is the `Bartender` photo the admin set and the other three come from the `Bartender` too (all `null` for the admin); a deleted bartender gets `AuthErrors.AccountDeleted` (403), and the shared `AccountService` then ends the session, so the bar app shows the login form. These three use `AdminOrBartender`; the profile image upload and removal (`PUT`/`DELETE api/account/image`) stay Admin-only. The admin email cannot be changed, because `SeedAdminAsync` would recreate the admin from `Admin:Email`. The Admin `Account/` feature folder has `AccountPage` (`/account`: a profile card with avatar, email and role, and a settings card with sections Profile image, Appearance (Light | Dark toggle group, `DarkModeService`), Password, Sessions, Sign out); the rest of the feature (`AccountApiClient`, `AccountDto`, `ChangePasswordRequest`, `AccountService`) and its dialogs `ChangePasswordDialog`, `SignOutEverywhereDialog` and `SignOutDialog` live in `OrderPoint.Shared/Account` (signing out asks for confirmation). Each app sends its own role; a user of the other role gets `InvalidCredentials`, exactly like a wrong password. 5 failed attempts lock an account for 5 minutes. A bartender with `MustChangePassword` gets `PasswordChangeRequired` (403) and must use `initial-password`, which works only while the flag is set (the shared `LoginForm` handles it: `AuthService.LoginAsync` returns true for `Auth.PasswordChangeRequired` (`ApiException.HasErrorCode`), and the form switches to a "choose your password" step that posts the temporary password just typed plus the new one and signs in with the returned tokens); an inactive bartender gets `AccountInactive`.
- Authorization: policy `AuthorizationPolicies.Admin` (role `Admin`) on every Admin endpoint, `AuthorizationPolicies.Bartender` (role `Bartender`) on the bar app's endpoints, and `AuthorizationPolicies.AdminOrBartender` on the ones both apps call (`GET api/orders`, `GET api/orders/{id}`, `PUT api/orders/{id}/decline`, `GET api/items`, `GET api/items/{id}`, `GET api/categories` and `GET api/categories/{id}` (the bar app's menu), `PUT api/items/status` and `PUT api/categories/status` (the bar app takes things off the menu when they run out), `GET api/floor-plan` and one area, table or fixture, `GET api/payments`, and (Bartender only) `GET api/tables/status`, `GET api/table-requests` and `PUT api/table-requests/{id}/done`, `GET api/account`, `PUT api/account/password`, `POST api/account/sign-out-everywhere`). Scalar sends a pasted bearer token (`SecurityTransformer`; the token is remembered with persistent authentication).
- Admin: the `Auth/` feature folder lives in `OrderPoint.Shared`, so the bar app reuses it. `AuthService` (one per circuit) keeps the tokens in `ProtectedLocalStorage`, refreshes one minute before expiry under a lock (parallel calls refresh once) and raises `SessionChanged`. `AccessTokenHandler` on every typed API client attaches the token; it reaches the circuit's `AuthService` through `CircuitServicesAccessor` + `ServicesAccessorCircuitHandler` (the documented pattern, since `IHttpClientFactory` handlers live in another DI scope). `AuthApiClient` is registered without the handler. `MainLayout` is the gate: it renders nothing until the session is loaded, then `LoginForm` instead of the page when signed out, so no page needs `[Authorize]`. `LoginForm` takes the app's `Role` (sent with the login, and picking the brand panel's tagline and three feature lines) and `AppName` ("Welcome back. Sign in to Admin web." and the footer). ### Observability

Everything goes to the Aspire dashboard over OTLP (structured logs, traces, metrics). An Admin page load shows as one trace: Admin → API → MediatR span → SQL.

- **ServiceDefaults** (`ServiceDefaultsExtensions`, only `AddServiceDefaults` and `MapDefaultEndpoints` are public):
  - **Instrumentation:** OpenTelemetry for ASP.NET Core, HttpClient and runtime, plus every `OrderPoint.*` source and meter and Blazor Server's built-in sources and meters (`Microsoft.AspNetCore.Components*`: navigation, events, circuits, rendering). Requests to `/health` and `/alive` are not traced.
  - **Resilience:** the HttpClient handler retries GET only (`DisableForUnsafeHttpMethods`), so a timed-out POST/PUT/DELETE never runs twice.
  - **Health endpoints:** `/health` (ready, every check) and `/alive` (only the `live` "self" check), Development only; Aspire's `WithHttpHealthCheck` uses `/health`.
  - **Health check timeout:** every check without its own timeout gets 5 s (a `PostConfigure<HealthCheckServiceOptions>`, so it also covers the Aspire integrations' checks). A stopped container behind Aspire's proxy hangs instead of refusing the connection; without the timeout `GET api/health` waited until the Admin gave up and showed the API itself as unreachable. Keep it well under the Admin's 10 s attempt timeout. `GetHealthEndpoint` turns the resulting `OperationCanceledException` into a readable "No response in time" error, and Redis' `RedisConnectionException` (a long diagnostic dump) into "Can't connect to Redis; it may be stopped...".
  - **Rule:** ServiceDefaults knows nothing about a specific database or storage; their telemetry and health checks come from the Aspire client integrations in the API.
- **Database:** Infrastructure registers `ApplicationDbContext` as usual; the API's `builder.EnrichNpgsqlDbContext<ApplicationDbContext>()` (package `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL`) adds its health check, Npgsql traces and metrics, and retries on transient errors (so never open a manual transaction without the execution strategy). `AddAzureBlobContainerClient` does the same for blobs. SQL shows up as trace spans, so `Microsoft.EntityFrameworkCore.Database.Command` logs only warnings.
- **Application telemetry** (`Telemetry/ApplicationTelemetry`, singleton, source and meter `OrderPoint.Application`):
  - `Mediator/TelemetryBehavior` (registered with `AddOpenBehavior`) wraps every command and query: a span named after the request (tags `orderpoint.request.name`, `orderpoint.request.type`, `error.type` = error code on failure, error status), the `orderpoint.request.duration` histogram (seconds, same tags), and a log: Information on success, Warning with the error code on failure. It never logs the request itself (passwords). Exceptions only mark the span and the metric; `GlobalExceptionHandler` logs them.
  - Business metrics: `orderpoint.orders.placed`, `orderpoint.orders.value` (EUR) from `CreateOrderCommand`, `orderpoint.auth.logins` (tags `orderpoint.user.role`, `error.type`) from `LoginCommand`. Add new instruments to `ApplicationTelemetry` with an `orderpoint.` name and a `Record...` method.
- **Event logs:** handlers whose outcome matters later (sign-ins, password changes and resets, signing out everywhere, bartender create/status/delete, order placed, order status changes, deletes, bulk status, price and category changes) log it with source-generated `[LoggerMessage]` methods (`private partial void LogX(...)` on a `partial` handler that takes `ILogger<THandler> logger`). Message templates use named placeholders (`{BartenderId}`, `{Email}`, `{ItemCount}`) so they become structured attributes; never log passwords or tokens. Queries and plain edits rely on the pipeline log. `RequestValidationExceptionHandler` logs failed validations (method, path, error codes), since they never reach MediatR.
- **Health in the Admin:** `GET api/health` (Admin policy, tag Health) runs `HealthCheckService` directly (a host concern, not a use case, so no MediatR) and returns each check with a display name (`self` → API, `ApplicationDbContext` → Database, `Azure_BlobContainerClient` → Storage, `StackExchange.Redis` → Cache, `pgweb` → Database browser, `storage-blobs-explorer` → Storage browser, `redisinsight` → Cache browser, `order-point-bar` → Bar web, `order-point-bartender` → Bartender web, `order-point-customer` → Customer web, `order-point-register` → Register web; add new checks to its `DisplayNames`, and the Admin card's title must equal that name). The Admin's `Health/` feature: the scoped `HealthService` calls it without `ApiService` (an unreachable API is a red result, not a snackbar), replaces the API check's duration with the Admin's round trip, and raises `Changed`; `MainLayout` checks after sign-in and every 30 s (`PeriodicTimer`). `HealthStatusIndicator`, the last item in the app bar (a text button with the coloured status icon; hovering slides the summary, e.g. "All systems operational", out to the left of the icon via a `max-width` transition toggled by `@onmouseenter`/`@onmouseleave`; no tooltip; links to the page), and `HealthPage` (`/system`, titled "Health", the Health link under System in the drawer: `HealthSummary` banner, one `HealthCheckCard` per component in three sections, "Core services" (API, Database, Storage, Cache), "Apps" (Bar web, Bartender web, Customer web and Register web: the API's `AddDevToolHealthCheck("order-point-bar")`, `("order-point-bartender")`, `("order-point-customer")` and `("order-point-register")` gets its `/`, Degraded when down) and "Developer tools" (Database browser, Storage browser, Cache browser), 3 cards per row, each titled with the check's name over the product (e.g. "Database browser" over "pgweb"), skeletons, a Refresh button that shows a spinner and "Checking..." while a check runs). When the API can't be reached or answers with an error, its card shows only a short description ("Not reachable from the Admin", "Responded with an error"); the exception goes to the Admin's log, not the page share it. Status colours, icons and texts come from `HealthStatusExtensions` (null = unknown, e.g. while the API is unreachable).
- **AppHost:** the API resource has an "API reference" link to `/scalar` in the dashboard.
- **Browser tools for data** (dev-only resources with their own link in the dashboard, already connected): `postgres.WithPgWeb()` (pgweb: browse tables, run SQL), `cache.WithRedisInsight()` (browse cache keys) and `storage.AddBlobs("storage-blobs").WithAzureStorageExplorer()` (Community Toolkit package `CommunityToolkit.Aspire.Hosting.Azure.Extensions`; browse, download and delete blobs). `storage-blobs` is the default name, so `AddBlobs` returns the blob service that already holds `images` instead of adding another one; `AddBlobContainer` on a blob service is obsolete, so the container stays on `storage`. All three are declared after the API, and their configure callbacks pass their `PrimaryEndpoint` to it with `WithReference` (no `WaitFor`). The API's `AddDevToolHealthCheck("pgweb")`/`("storage-blobs-explorer")`/`("redisinsight")` (`Extensions/HealthCheckExtensions.cs`) registers an `HttpHealthCheck` (`HealthChecks/`, GET `/` through a named HttpClient with base address `https+http://<service>`, because Aspire serves RedisInsight over https with the dev certificate while pgweb and Storage Explorer stay on http) only when Aspire supplied a `services:<service>` URL, with failure status `Degraded`: a stopped tool turns the Admin amber, not red, and Aspire's `/health` still answers 200.

### Validation is duplicated on purpose; keep it in sync

Field rules live in several places. Changing one means changing all of them:
1. Domain entity `Create`/`Update`: required and positive checks only (no max lengths)
2. API request validator (FluentValidation, messages like `"Name is required"`): required, positive, max length, enums
3. EF entity configuration (`HasMaxLength`, `IsRequired`) plus a migration if the schema changes
4. Admin request class DataAnnotations (messages end with a period: `"Name is required."`): required, positive, max length

The guest's card (`CreateOrderEndpoint` and the customer app's `CreateOrderCardRequest`) follows the same rule: 13 to 19 digits with spaces, `MM/YY`, a 3 or 4 digit CVC; only the API checks that it hasn't expired.

## Admin web conventions (`web/OrderPoint.Admin`)

### Structure

- Feature folders: `<Feature>/Api` (`<Feature>ApiClient`, `Requests/`, `Responses/`), `Components/`, `Dialogs/`, `Dtos/`, `Enumerations/`, `Pages/`, `Sorting/`. Cross-feature code is in `Shared/` (`Components/`, `Constants/`, `Extensions/`, `Layout/`, `Pages/`). Reusable formatting helpers are `internal static` extension methods in `Shared/Extensions/<Type>Extensions.cs` (e.g. `DateTimeOffset.ToRelativeTime()` → "2 h ago"), not private methods on a page.
- Code more than one app needs lives in the Razor class library `web/OrderPoint.Shared` (namespaces `OrderPoint.Shared.<Folder>`, same folder layout: `Account/` (all but `AccountPage`), `Auth/`, `Components/` (`StatefulView`, `ChipSkeleton`, `StatusMessage`, `SettingsSection`, `QuantityStepper`, `LiveIndicator`, `TabCount`, `ListPager`, `StableHeight`), `Constants/` (`ImageUrls`, `ImageStyles`, `DeclineReasons`), `Dtos/` (`PaginationDto`, `ImageFileDto`), `Errors/`, `Extensions/` (Configuration, CultureInfo, DateTimeOffset, Int, ImageFileDto, OrderDto, OrderPayment, OrderStatus, PaymentChannel, TimeZoneInfo), `Layout/` (`AppTheme`, `ReconnectModal`), `Bartenders/` (`BartenderAvatar`), `Orders/` (`OrderDto`, `OrderItemDto`, `OrderBartenderDto`, `OrderStatus`, `OrderPaymentFilter`, `PaymentChannel`, `PaymentSortBy` + `PaymentSorting` in `Sorting/`, `OrderAvatar`, `DeclineReasonField`, and `Receipt`, the printable till receipt, which prints itself with `PrintAsync` (collocated `Receipt.razor.js` copies its markup into a hidden iframe); the rest of the feature stays in the Admin), `Items/` (`ItemCardContent`, `ItemCardImage`, `ItemCardContentSkeleton`), `Tables/` (`AreaDto`, `TableDto`, `FixtureDto`, `FloorPlanMoveDto`, the enums, `FloorPlanMap`, `TableRequestItem`), `Menu/` (the guests' menu from `GET api/menu`: `MenuCategoryDto`, `MenuItemDto`, `MenuApiClient`, and the order-pad pieces `MenuCategoryCard` and `MenuItemRow` (the app passes `MaxQuantity`) with their skeletons; used by the customer app and the Bartender app), `Services/` (`ApiService`, `TimeZoneService`, `DarkModeService`), `Images/` (the bar and customer apps' image proxy), `wwwroot/images/` (logo, placeholder)). Admin-only helpers (e.g. `DashboardPeriodExtensions`) stay in the Admin's `Shared/`.
  - **Static files:** the library's `wwwroot` files and collocated JS are served under `_content/OrderPoint.Shared/` (e.g. `ImageUrls.Logo`); its scoped CSS reaches each app through the app's own `<App>.styles.css`.
  - **Visibility:** types stay `internal`; the apps see them through `<InternalsVisibleTo>` in `OrderPoint.Shared.csproj` (add each new web app there). Components stay `public`.
  - **Usings:** the Razor SDK has fewer implicit usings than the Web SDK, so files there add e.g. `Microsoft.Extensions.Logging` and `System.Net.Http.Json` themselves.
- Every component is split into `X.razor` (markup only) and `X.razor.cs` (`public sealed partial class X`). No `@code` blocks.
- Visibility: components are `public` (Razor requires it), so DTOs, enums and `PaginationDto` used as component parameters are `public`. Everything else (API clients, requests, responses, sort enums, `XSorting` helpers, services) is `internal`.
- Inject with `[Inject] private T Name { get; set; } = null!;`. Parameters use `[Parameter]` and `[EditorRequired]` where mandatory.
- Add new namespaces that pages use to `_Imports.razor`.

### API calls

- API clients are `internal sealed`, use relative URIs without a leading slash (`api/items?...`), escape user text with `Uri.EscapeDataString`, are typed HttpClients (`internal sealed class XApiClient(HttpClient httpClient)`), call `ApiExceptionHelpers.ThrowApiExceptionAsync` on non-success, and unwrap `.Data` from the response record. Register them in `Program.cs` with `builder.Services.AddHttpClient<XApiClient>(ConfigureApiClient).AddHttpMessageHandler<AccessTokenHandler>()` (base address in `ConfigureApiClient`; the handler attaches the access token). Only `AuthApiClient` is registered without the handler. Typed clients are transient, so never store one in a singleton.
- Pages and dialogs call API clients **only** through `ApiService`, which owns all API error handling and snackbars:
  - Queries: `T? result = await ApiService.ExecuteAsync(() => client.GetXAsync(...))`. Returns `null` on failure (error snackbar already shown), so fall back: `Items = Pagination?.Items ?? [];`.
  - Mutations: `bool isSuccess = await ApiService.ExecuteAsync(() => client.CreateXAsync(request), $"Item {request.Name} created successfully");`. Shows the success snackbar on success and the error snackbar on failure; reload the list only when `isSuccess`.
  - Autocomplete `SearchFunc`s pass MudBlazor's `CancellationToken` to both the client and `ExecuteAsync`, so cancelled searches are silent: `return categories ?? [];`.
  - Pages never inject `ISnackbar` for API results.
  - Snackbars stay 2 s in every app (`SnackbarVisibleMilliseconds` in each `Program.cs`; MudBlazor's default is 5 s).
  - `ApiService` logs unexpected exceptions (network, parsing); expected API errors (ProblemDetails), cancellations and `SessionExpiredException` are not logged.

### Pages and dialogs

- **Sections load independently and in parallel.** Each section of a page (a table, a highlight card, a list in a dialog) has its own `Get<Section>Async` method and its own `IsLoading<Section>` flag; the method ends with `StateHasChanged()` so the section renders as soon as its data arrives. `OnInitializedAsync` and post-mutation reloads start independent sections with `await Task.WhenAll(...)`; never await independent loads one after another. Only dependent steps stay sequential (mutation → reload).
- Highlight sections above a list (Categories: top 5 by item count; Items: spotlight cards for newest, last edited, highest and lowest price; Bartenders: team strip with active avatars, active/inactive balance and newest member; Orders: status pipeline of `OrderStatusCard`s, Pending → Accepted → Active → Completed plus Declined and Cancelled, where clicking a card filters the timeline and clicking it again clears the filter; the counts follow the bartender and payment filters) reuse the list endpoint with `pageSize`/`sortBy`/filters (the pipeline makes one `pageSize: 1` call per status and reads `TotalCount`); they do not get their own endpoints.
- Dashboard (`Dashboard/Pages/DashboardPage`, route `/`): bento `MudGrid` (4 KPI cards; revenue trend area chart + busiest-times heat map + category donut + "Payments by method" (`PaymentMethodsSummary`: cash, card at the register, card online as outlined papers with amount, share bar and "12 payments · 45%"; `PaymentMethodsSummarySkeleton`) on the left, tall "Right now" live panel on the right; top items, bartender leaderboard, recent orders below). Tiles use `DashboardTile` (icon, title, optional `HeaderContent`, `StatefulView`, optional `ContentHeight` that keeps loading/empty states as tall as the content; the revenue tile passes `RevenueTrendChart.ChartHeight` so the left column always matches the "Right now" panel) and `DashboardKpiCard` (value + ▲/▼ change chip vs previous period, `IsLowerBetter` for service time). A `MudToggleGroup` period switch in the `PageHeader` reloads the period sections; the live panel (open orders, longest wait, today so far: orders, completed, revenue, average order; "At the register": To pay and Refunds due, each with count and total) refreshes every 30 s with a `PeriodicTimer` disposed with the page. Top items rows open `ItemDetailsDialog`, leaderboard rows open `BartenderOrdersDialog` (each fetches the full DTO first), recent orders open `OrderDetailsDialog`; all three lists highlight the hovered row with `var(--mud-palette-table-hover)`. All three charts are hand-built for a consistent hover experience (MudChart has no hover-anywhere crosshair and its tooltips are small): the revenue trend (SVG area + crosshair), the busiest-times heat map (HTML grid) and the top-5 category donut (SVG ring; each legend row shows the category's 24px picture (`CategoryRevenueDto.CategoryImageUrl`), and hovering a segment or legend row shows the category, with its picture, in the centre). Revenue trend and heat map: transparent per-column slots set the hovered index and show a `MudTooltip` with `TooltipContent` (body2 label + h6 value), SVG coordinates are formatted with `CultureInfo.InvariantCulture`, colours come from palette CSS variables (`var(--mud-palette-primary)`, `rgba(var(--mud-palette-primary-rgb), …)`). In Razor loops, copy the loop variable into a local before using it inside child content or lambdas (`int rank = i + 1;`), otherwise every row renders the final value.
- List pages: `private const int PageSize` (10 for `DataTable`, `DataAccordion` and `DataTimeline`, 16 for the 4-column `DataGrid` (4 rows), 5 for `DataList` in a dialog); one `Get<Plural>Async(int pageNumber)` that reads the current search/sort/filter properties; search, sort and filter changes call it with `pageNumber: 1`; `OnPageChangedAsync(int pageNumber)`.
- Sorting is passed as the sort enum's name: `SelectedSortBy = nameof(ItemSortBy.CreatedAtUtcDesc)`; labels and icons come from `<Feature>Sorting.GetSortByLabel/GetSortByIcon`. Item dropdowns use `ItemSorting.SortByOptions` (name, price, created); `UpdatedAtUtcDesc` only feeds the "Last edited" spotlight. Category dropdowns use `CategorySorting.SortByOptions` (name, display order, created); `ItemsCountDesc` only feeds the top 5 cards.
- Create/update/delete/details are MudBlazor dialogs opened from the list page (not separate pages). Dialogs return the request object via `MudDialogInstance.Close(DialogResult.Ok(Request))`; the page performs the API call and reloads. Use early returns: `if (dialogResult.Canceled) { return; }`. Read-only features (Orders) only have a details dialog (whose only action is declining an open order). Orders show their payment through the shared `OrderPoint.Shared/Extensions/OrderPaymentExtensions` (`GetPaymentText` "To pay" / "Paid in cash" / "Paid by card" / "Paid online" / "Refund due" / "Refunded" / "Nothing to pay", `GetPaymentColor`, `GetPaymentIcon`, `GetSourceText`): an outlined chip below the total on the Orders timeline tickets (the "Payment" filter select is `FitContent`), and in `OrderDetailsDialog` a Source and a Taken by row plus a Payment paper (icon, "Payment" and the chip, then one row of equal outlined fact tiles, `PaymentFacts`: Amount due and Pays at / Why for an unpaid order; Amount, Paid, Paid to ("Guest, online" for the customer app), plus Cash received and Change for cash; a refund due or refunded is two rows of three: Amount, Paid, Paid to, then Cash received and Change (cash) or Method and Refund to (card), then Refund ("Due at the register") or Refunded).

- Payments (`Payments/` feature folder, `PaymentsPage` at `/payments`, "Payments" in the drawer after Orders and in the search's pages): the `PageHeader` holds the dashboard's period switch; four `PaymentTotalCard`s (icon, label, amount as `RollingNumber`, caption; `PaymentTotalCardSkeleton`) show Cash, Card at the register and Card online for the period (the dashboard's `payment-methods` endpoint) and Refunds due from any day (`live`); below them a `DataLedger` of `GET api/payments` (`Payments/Api/PaymentApiClient`, 10 per page) with search, sort (`PaymentSorting`: Paid, Order number, Total), How (`PaymentChannel` with icons), Status (Paid, Refund due, Refunded) and a Paid to bartender autocomplete. A click selects the row and the `SideContent` panel (`PaymentReceiptPanel`, sticky) shows it as the shared `Receipt` with Print and Order details (opens `OrderDetailsDialog`), or "Select a payment". Everything reloads silently on `OrdersChanged`; the selection follows the reloaded payment by id.
- Global search (`Search/` feature folder):
  - **Opening:** the `SearchTrigger` in the app bar, or Ctrl+K / ⌘K. `wwwroot/js/search.js` registers the shortcut and calls `MainLayout.OpenSearchFromShortcutAsync` through a `DotNetObjectReference`.
  - **Focus and keys:** `GlobalSearchDialog` sets `DefaultFocus="DefaultFocus.FirstChild"` on the `<MudDialog>` component itself. `MudDialog` wraps its content in a focus trap that reads this parameter, not `DialogOptions.DefaultFocus`, and otherwise moves focus from the field to the dialog element. ↑/↓/Enter use `MudDialog.OnKeyDown`, which the container's key interceptor fires for any key inside the dialog.
  - **Searching:** no backend of its own. It runs the existing list and search endpoints in parallel, 5 results per group: orders by number or table, items, categories and bartenders, plus tables by code or area name, matched locally in the (cached) `GET api/floor-plan` ("Table T7", "Terrace · 4 seats", " · Inactive"). Pages whose title contains the query are matched locally and listed first. Each group has its own loading flag and skeleton rows, and a new query cancels the previous one.
  - **Empty query:** shows "Recent" (the last 5 opened results, per browser in `ProtectedLocalStorage`) and "Pages".
  - **Keyboard:** ↑/↓ move the highlight, Enter opens, Esc closes. A `SearchResultRow` that becomes active scrolls itself into view after rendering (`scrollSearchResultIntoView`, `block: "nearest"`), so keyboard navigation follows long result lists.
  - **Opening a result:** the dialog returns a `SearchResultDto`, and `SearchService.OpenAsync` navigates to a page (a table to `/tables?table=T7`, kept in Recent), or fetches the record fresh by id and shows the same details dialog the dashboard uses (bartenders open `BartenderOrdersDialog`).
  - **Items only:**
    - "Move" opens `ChangeItemsCategoryDialog`: a category autocomplete with images and the clear fix, plus a warning when the target category is inactive.
    - "Adjust price" opens `AdjustItemsPriceDialog`: mode, a value with a % or € suffix, and a live old → new preview. It uses `PriceAdjustmentMode.Apply` from `Shared/Extensions`, which mirrors the API's calculation. Confirm is disabled while the value is invalid or any new price would not be positive. `UpdateItemDialog` offers the same modes for one item (Price select + Value with the % or € suffix and "€4.50 → €4.95" as helper text; Set starts with the current price, the change modes start empty, meaning no change) and sends the resulting price; `CreateItemDialog` keeps a plain Price field with the € suffix.
    - Both dialogs return their request object, with the category name as `[JsonIgnore]` for the success message.
- A dialog that changes data the page shows (e.g. items inside `CategoryDetailsDialog`) exposes an `EventCallback On<Thing>Changed` parameter and invokes it after a successful mutation; the page passes `EventCallback.Factory.Create(this, ...)` in the `DialogParameters` and reloads. Do not rely on the dialog result for this: closing with X/Escape returns `Canceled`.
- Dialogs and components initialise state and load data in `OnInitialized`/`OnInitializedAsync` (parameters are already set). Do not use `OnParametersSet`: it runs again whenever the dialog provider re-renders, which resets forms and reloads lists. Exception: display-only chart components (`RevenueTrendChart`, `BusiestTimesHeatMap`, `CategoryRevenueDonut`) build their `ChartSeries`/labels from parameters in `OnParametersSet`, so charts are rebuilt only when their data changes, not on every render. `RollingNumber` and `StableHeight` also react to parameter changes there (a new value, loading starting).
- Forms: `EditForm` + `DataAnnotationsValidator`, MudBlazor inputs with `Variant.Outlined`, `HelperText`, `Immediate="true"`. Helper texts fit on one line at the field's width (about 40 characters for a half-width field in a Medium dialog). Fields side by side get `Class="flex-1"` plus `Style="min-width: 0"`, so a longer helper text can't make one wider than the other. `OnValidSubmit` only closes the dialog. Add `OnInvalidSubmit` + `IsFormSubmitted` only for inputs not covered by DataAnnotations `For` (e.g. a `MudAutocomplete` showing `Error`/`ErrorText`).
- Lookup autocompletes (category on Items, bartender on Orders): the API client's `Search<Plural>Async` returns the first 5 by name for empty text, else calls `api/<plural>/search`. Options use an `ItemTemplate` with a 24px picture next to the name (`MudImage` with `ObjectFit.Cover` and the placeholder for categories, `BartenderAvatar Size="Size.Small"` for bartenders); the input itself stays plain text. A `Clearable` autocomplete gets a `@ref` and `OnClearButtonClick` calling its `OpenMenuAsync()`, because MudBlazor 9 empties the list on clear without searching again ("No ... found" instead of the 5 defaults).

Each layout has a `<Real>Skeleton` component next to the real one (`ItemCardContentSkeleton`, `OrderTicketSkeleton`, `CategoryRowSkeleton`, `RevenueTrendChartSkeleton`, ...), built from `MudSkeleton` (default wave) and the shared `ChipSkeleton`. Every placeholder line sits inside a `MudText` with the real `Typo`, so heights match, and static labels stay real text (e.g. the live panel's status names). List components take `LoadingTemplate` (one row/card) and repeat it inside their real containers, at most 3 rows (the item grid: 3 rows of 4 cards); skeleton lists elsewhere (dashboard lists, donut legend) also stop at 3, while charts, the heat map and rows of cards keep their real shape; `StatefulView`, `HighlightCard` and `DashboardTile` take `LoadingContent`. Without them the spinner remains. `App.razor` recolours the wave with the text colour so it shows in dark mode. Pages only pass the skeleton; no skeleton markup in pages or real components.
- Times are stored and sent as UTC. The Admin shows them in the browser's time zone: `TimeZoneService` (scoped, loaded once per circuit in `MainLayout` from `Intl.DateTimeFormat().resolvedOptions().timeZone`, UTC if unknown) and `dateTime.ToDisplayDateTime(TimeZoneService.TimeZone)` everywhere a date-time is displayed ("Today 14:30", "Yesterday 9:15", else the locale's short date and time, no seconds). For any other format convert with `ToTimeZone(...)` first; never call `ToString` on a `*AtUtc` value directly. `DashboardApiClient` sends `TimeZoneService.TimeZone.Id` as `timeZone`. Relative times (`ToRelativeTime`) need no conversion.
- Formatting follows the viewer's browser: `UseRequestLocalization` (all cultures, from `Accept-Language`) plus a middleware in `Program.cs` that swaps in `CultureInfo.ToDisplayCulture()` (`OrderPoint.Shared/Extensions/CultureInfoExtensions.cs`): the locale's number, date and 12/24 h formats, but English day and month names to match the UI, and amounts always in euros with 2 decimals. So format with `CultureInfo.CurrentCulture` (`"C"` for money, `"t"`/`"g"` and `GetShortMonthDayPattern()` for dates, `Uses12HourClock()` for hour-only labels), never hardcode `HH:mm` or `dd.MM`, and use `InvariantCulture` only for CSS/SVG numbers.
- Order status colours and icons come from `OrderStatus.GetColor()`/`GetIcon()` in `OrderPoint.Shared/Extensions/OrderStatusExtensions.cs`; use them everywhere a status is shown (pipeline, timeline dots, chips, details timeline).
- Admin DTOs, enums and sort enums mirror the API ones by hand. When an API contract changes, update the Admin copy too.
- Use MudBlazor components and `Icons.Material.Filled.*`; avoid custom CSS. Colours come from the theme in `OrderPoint.Shared/Layout/AppTheme.cs`, never hardcoded hex. The theme is tweakcn's "vercel" (monochrome dark and light palettes: primary is black in light mode and white in dark mode, so `PrimaryContrastText` is set per palette; Geist font, 8px radius, no shadows in either mode (every theme elevation is `none`, and the global `<style>` block in `App.razor` also removes the filled-button shadow), buttons not uppercase; every elevated surface gets a `lines-default` border from that same `<style>` block, so use `Elevation="0"` for a surface that must stay borderless (always on `MudTimelineItem`: the border would squash its filled dot into an oval; its `Icon` parameter is ignored in MudBlazor 9.6, so put a small `MudIcon` in `ItemDot`); hover is a background change, never a lift); the app bar and drawer are separated by `lines-default` borders, not elevation. Dark mode and an open drawer are the defaults; both are remembered per browser in `ProtectedLocalStorage`. Dark mode lives in the scoped `DarkModeService` (`OrderPoint.Shared/Services`): `MainLayout` applies it and re-renders on `Changed`, and the account page's Appearance section changes it (there is no app bar toggle). Elsewhere: dialogs use `Class="mud-background"`, borders use `var(--mud-palette-lines-default)`.
- Razor attribute style:
  - Plain for literals, enum values and type parameters: `Label="Sort by"`, `Clearable="true"`, `Variant="Variant.Outlined"`, `T="string"`, `TItem="ItemDto"`.
  - `@` for anything that references code, including directive attributes: `Items="@Items"`, `OnClick="@Cancel"`, `@bind-Value="@Request.Name"`, `Icon="@Icons.Material.Filled.Add"`.
  - `@(...)` for lambdas and expressions: `OnClick="@(() => ShowDeleteItemDialogAsync(item.Id, item.Name))"`.
- The mockups in `design/` are inspiration only; the owner decides layout and fields per screen. Do not add fields or screens from a mockup unless asked.

## Bar app conventions (`web/OrderPoint.Bar`)

Same structure and rules as the Admin (feature folders, `X.razor` + `X.razor.cs`, typed API clients called through `ApiService`, skeletons, live reloads), but built for phones and tablets.

- **Shell:** `Shared/Layout/MainLayout`: a dense app bar (logo, "OrderPoint / Bar" (the app bars name the app without "web": Admin, Bar, Bartender, and the Register next), `LiveIndicator` showing the `OrdersHubService` state: green Live, amber Connecting, red Offline) and `BottomNavigation`, fixed to the bottom (Orders `/`, which also matches `/orders/...`, Tables `/tables`, My shift `/shift`, Menu `/menu`, Account `/account`); `MainContent` is padded by its height. Snackbars sit at the top. Pages have one `h1` (`Typo.h6`/`h5`, no `PageHeader`). Empty states use a short title plus `StatefulView.EmptyStateDetail` for the hint on a second line ("Nothing in progress" / "Accept an order from the queue."). Dialogs are only for confirmations (sign out, sign out everywhere); anything else (details, forms) is its own page with a back arrow before the h1 (`MudIconButton` with `Href` to the parent page), e.g. `OrderDetailsPage`, `DeclineOrderPage`, `MenuItemPage`, `ChangePasswordPage`. Search fields use `Placeholder`, not `Label`, so the text sits inside the field next to the search icon.
- **Orders (`/`):** Queue / Mine / Done tabs (`OrdersTab`; the scoped `OrdersTabState` remembers the last one for the session, and on a tablet the order open in the panel (`SelectedOrderId`), so coming back from My shift, Account or an order opens it again; the tab bar sticks under the dense app bar while scrolling (a wrapper in the page background, `top: 48px`), and it is a paper like the tickets (border, theme radius, `overflow: hidden`) holding a row of three `flex-1` text buttons with a 2px primary underline on the selected one, not `MudTabs`, whose tab bar only grows as wide as its tabs; the selected tab's list renders below), each an `OrderTicketList` of `OrderTicket`s (number tile, table, "Placed 3 min ago" or "Completed Today 14:30", total, status chip, one line per item, note, and "Taken by Ana Horvat" / "Taken by you" for an order a bartender entered); the place is `GetPlaceText()`, and `OrderDetails` adds " · taken by ..." to its placed time and shows "Show on map" only for a table. On an open order (Pending, Accepted, Active) the placed time turns amber (warning, semibold) from 5 minutes and red (error) from 10, so the longest waits stand out. Queue: every Pending order, oldest first (new ones highlighted with `NewOrdersTracker`). Mine: my Active, then my Accepted orders. Done: my Completed and Declined orders finished since the day start (`TimeZoneInfo.GetTodayStartUtc(Configuration.GetBusinessDayStart())`, `OrderPoint.Shared/Extensions/ConfigurationExtensions` and `TimeZoneInfoExtensions`), newest first. Each status is one `GET api/orders` call of up to 50 (`bartenderId` = `AuthService.UserId`), no paging. Tab counts are `TabCount` pills with `RollingNumber`. Every tab reloads silently on `OrdersChanged`, and a 30 s timer re-renders so relative times move on. A search field ("Order number or table", dense, in the same sticky header above the tabs) uses `GET api/orders?searchQuery=`: while it has text the tab bar is hidden and the list shows matching orders of any status and any bartender, newest first, 20 at a time with "Show more" and an "n orders found" caption; the tickets add who handles them (`OrderTicket.ShowsBartender`: "· Ana Horvat" or "· you"). A result opens like a tab ticket (phone page or tablet panel); `OrdersChanged` reloads as many results as are shown (whole pages, at most 100), and a response for an older search text is ignored. Clearing the field brings the tabs back.
- **Requests strip:** under the Orders page's search (in its sticky header) every open guest request is a `TableRequestItem` with the table ("T7 · Call bartender"), full width, one under the other; Done marks it done (snackbar), a tap opens the table on the map (`/tables?table=T7`). It reloads on `TablesChanged`.
- **Order details:** `OrderDetails` loads the order by id, follows it live (`OrdersChanged`; a failed reload keeps what is shown) and shows the header (number tile, table, placed, status), one row per item (40px image, "**2×** name", line total), the note, the total, the status steps with times, and who handles it ("Handled by you"). Its action bar (big buttons, always at the bottom: on a phone fixed to the screen above the bottom navigation, with room left under the details; in the tablet panel, which grows with the details up to the screen's height, right below them, the details scrolling inside it once they don't fit) matches what this bartender may do: Pending → Decline + Accept (any bartender), Accepted and mine → Decline + Start, Active and mine → Complete; other bartenders' orders have no buttons. Decline opens `DeclineOrderPage` (`/orders/{id}/decline`: back arrow, the order's `OrderTicket`, a warning, the shared `DeclineReasonField`, and a large "Decline order" button with a spinner, disabled while the reason is empty or the order can no longer be declined by this bartender; a refusal reloads the ticket, success goes to `/`; the back arrow returns to the tablet panel when `OrdersTabState.SelectedOrderId` is this order, else to `/orders/{id}`), and a declined order shows its reason under the status steps. While the API answers, the tapped button shows a spinner and every button is disabled (`WorkingAction`, an `OrderAction`). After Accept or Start it stays and reloads; after Complete it raises `OnFinished`; a refused change (409, e.g. accepted by someone else first) shows the API's message and reloads. The actions go through `OrderApiClient.Accept/Decline/Activate/CompleteOrderAsync` (`PUT api/orders/{id}/<action>`, no body).
- **Phone vs tablet:** `OrdersPage` subscribes to `IBrowserViewportService`; below 600 px (`Breakpoint.Xs`) a ticket opens `/orders/{id}` (`OrderDetailsPage`: back arrow, `OrderDetails`, its buttons sticky above the bottom navigation; `OnFinished` goes back to `/`), from 600 px the page splits: the list (5/12) and a sticky details panel (7/12) with the selected order (`OrderDetails IsInPanel="true"`, keyed by id; `OnFinished` and `OnClose` (the × after the status chip, shown only when `OnClose` is set) clear the selection; the selected ticket gets the `table-hover` background and a primary border) or a "Select an order" prompt.
- **Tables (`/tables`):** the floor plan the admin set up (`Tables/Api/TableApiClient`: `GET api/floor-plan`) with live order status (`GET api/tables/status`, Bartender policy, not cached: `TableStatusDto(TableId, PendingCount, InProgressCount, OldestOpenOrderPlacedAtUtc)` for every table with open orders, built by `GetTablesStatusQuery` from `IOrderRepository.GetByStatusesAsync`). No visible title (its `h1` is visually hidden, for screen readers): the map uses the screen between the app bar and the bottom navigation (`TablesPage.ScreenHeight`, also the skeleton's height). Area tabs (the Orders tab bar's look) when there is more than one area; the shared `FloorPlanMap` read-only in a bordered frame that fills the rest of the screen and scrolls both ways, so a bartender pans it with a finger (the scroll area is a size container; the map is `max(columns × 40px, 100cqw, 100cqh × columns / rows)` wide, so cells are at least 40px and the grid always fills the frame), its `TableStyle` tinting a table's border and background (amber: waiting for a bartender, blue: in progress, red: an open order waited 10+ minutes, the ticket rule) and its `TableContent` adding an upright count badge in the corner; the legend is a small paper in the frame's bottom-left corner (11px text, 8px dots), outside the scroll area, so it stays put while panning. A tapped table shows `TableOrdersPanel` (table, area, seats, a warning when it is closed, its open orders as `OrderTicketList` with who handles them, oldest first; `GET api/orders?tableId=` once per open status, up to 50): on a phone as a bottom sheet above the bottom navigation (50vh; the map's frame shrinks by as much, so it never hides under the sheet), from 600 px as a side panel next to the map (flex 7 : 5, the panel scrolls inside the screen's height) with a "Select a table" prompt. A ticket opens the order: its own page on a phone, on a tablet the Orders page with it in the panel (`OrdersTabState.SelectedOrderId`). Taps on fixtures do nothing. Reloads silently on `OrdersChanged` (status and the open table's orders) and `TablesChanged` (floor plan); a 30 s timer re-renders so the colours move on. `/tables?table=T7` (the map icon button next to the table in `OrderDetails`, "Show on map") selects that table and its area. Whenever a table is selected (tap or link), the collocated `TablesPage.razor.js` scrolls it to the middle of the map after the render (`scrollIntoView`, smooth, centred), so it is also visible above a phone's sheet. Tables with an open guest request get a bell badge (`RoomService`, primary) in the corner opposite the order count, the legend explains it ("A guest is asking"), and the table's panel lists its requests above its orders as `TableRequestItem`s (icon, "Call bartender", "Asked 2 min ago", a Done button); requests reload on `TablesChanged`.
- **My shift (`/shift`):** "Your day since 06:00" (the configured day start, locale time format) and four `ShiftTile`s (2 per row on a phone, 4 from 600 px) from `GET api/shift` (`ShiftApiClient` sends the time zone): Queue (pending), Mine (accepted or active), Completed today and the average service time (placed to completed), with rolling numbers, skeleton tiles, and a silent reload on `OrdersChanged`. The three order tiles set `OrdersTabState` and open the Orders page on that tab. Below them "My day" (h2) loads `GET api/shift/day` in parallel (own loading flag, `ShiftDaySkeleton`, empty state "Nothing served yet"): `ShiftDay` shows Served (€) and Items served, `ShiftHoursChart` (hand-built HTML bars, counts above the bars because phones have no hover, hour labels every 1/2/3 hours depending on the shift's length, locale 12/24 h) on the left (7/12 from 600 px) and "Most served" (the Admin's top items row look: 40px image, "9×", share bar, revenue) on the right (5/12).
- **Menu (`/menu`):** to answer guests, and to take things off the menu when they run out (`Menu/`: `MenuApiClient` over `GET api/categories` (up to 100, `DisplayOrderAsc`), `GET api/categories/{id}` and `GET api/items` (one category, `NameAsc`, 20 per page), with its own copies of the item and category DTOs, enums and sort enums). `MenuPage` is a grid of `MenuCategoryCard`s in menu order (centred 56px thumbnail, greyscale when inactive; the name below it, up to 2 lines; an Active/Inactive chip below that; 3 per row on a phone, 4 from 600 px, 6 from 960 px) with a sticky search (debounced, category name). A card opens `MenuCategoryPage` (`/menu/{id}`, back arrow to `/menu`; the bottom navigation's Menu matches it): header with the category picture, name (h1) and status chip, a warning when the category is inactive, a sticky item search, `MenuItemRow`s (56px picture, name, "Portion 0.3 · description" on one line, price) and a "Show more" button that appends the next page instead of a pager. Unavailable items (`ItemDto.IsActive`, same rule as the Admin) stay listed with a greyscale picture and an "Unavailable" chip. A row opens `MenuItemPage` (`/menu/{categoryId}/items/{id}`, loads `GET api/items/{id}`, back arrow to the category; `MenuItemDetails`: a warning saying why an unavailable item can't be ordered, then the Admin's item card (`ItemCardContent` with the whole description)). The item page has an "Available to guests" switch in a paper above the details ("Turn off when it runs out."; the item's own status), and the category page a switch after the name in its header (labelled Active or Inactive) instead of the status chip. The three pages follow `OrdersHubService.MenuChanged` live without skeletons (a failed reload keeps what is shown; the category page reloads every page shown so far, so "Show more" stays).
- **Account (`/account`):** a profile card (photo the admin set or the name's initials, full name, email and phone number with icons, Bartender chip, "Your name, email, phone number and photo are set by the admin.", all from `AccountService`) and a settings card of the shared `SettingsSection`s (icon, title, description, the control below at full width): Appearance (Light | Dark, `DarkModeService`), Password (`ChangePasswordPage` at `/account/password`: the shared dialog's fields and `ChangePasswordRequest` on a page, returns to `/account` after saving), Sessions (`SignOutEverywhereDialog`), Sign out (`SignOutDialog`).

## Bartender app conventions (`web/OrderPoint.Bartender`)

The Bar app's structure and rules (feature folders, `X.razor` + `X.razor.cs`, typed API clients through `ApiService`, skeletons, live reloads, pages with a back arrow, dialogs only for confirmations), for the bartender who takes orders at the tables and at the counter on a phone or tablet. Bartenders sign in with the same account as in the Bar app (`LoginForm Role="UserRole.Bartender" AppName="Bartender web"`); the same person may use both apps, or the Register later. It takes no payments: the guest pays at the register.

- **Shell:** the Bar app's `MainLayout` (dense app bar with "OrderPoint / Bartender" and `LiveIndicator`, content in a `MaxWidth.Small` column) and `BottomNavigation` with Tables (`/`, which also matches `/tables/...` and `/counter/...`), Orders (`/orders`) and Account (`/account`, the Bar app's account and change password pages, copied). Ports 7036/5136; the AppHost passes `BusinessDay__StartHour` and `Images__StorageUrl` like for the Bar app.

## C# style

- File-scoped namespaces matching the folder path; `using` directives at the top, outside the namespace.
- Classes are `sealed` by default and as little visible as possible (see Ground rules).
- Primary constructors for DI (handlers, repositories, API clients, exception handlers, services).
- Explicit types for locals (`Result<ItemDto> result = ...`, `Item? item = ...`, `string requestUri = ...`, `int i`). `var` only when the type is obvious from the right side: `new`, casts, mapper calls (`ToXDto()`), and generic calls naming the type (`GetRequiredService<T>()`, `Enum.Parse<T>()`). Never `var` for built-in types.
- Always braces, `is null` / `is not null`, collection expressions `[]`.
- Async methods end in `Async` and take a `CancellationToken`.
- Lines are at most 120 characters. When a call does not fit, break its arguments one per line; short calls stay on one line.
- Formatting follows `app/.editorconfig`: 4 spaces, UTF-8 **with BOM** for `.cs`, `.razor` and `.csproj` files, no final newline. Line endings are handled by git (`.gitattributes`: LF in the repo, CRLF in the working tree); keep CRLF when creating or editing files.

## Adding a new entity end-to-end (checklist)

Domain entity + errors (+ sort enum) → repository interface → EF config + EF repository + DbSet + registration → migration → DTO + mapper → commands/queries (cached reads with `CacheKeys`/`CacheTags`, writes implementing `ICacheInvalidatingCommand`, see Caching) → endpoints with validators and `RequireAuthorization(AuthorizationPolicies.Admin)` → Admin DTOs/enums/sorting → API client + requests/responses + registration → page + dialogs → nav link in `Shared/Layout/MainLayout.razor` (add it, or check it already exists; Orders and Bartenders already have links) → `dotnet build app/OrderPoint.slnx -c Release`.
