# OrderPoint

Order management system for a bar: customers order from their phones via QR code, bartenders fulfil orders in real time, and the owner manages everything in an admin web app. The **API**, the **Admin web app**, the **bartender app** and the **customer app** all exist.

## Ground rules

- **Never run `git commit`, `git push`, `git merge`, `git rebase`, `git reset`, `git stash` or `gh pr create`.** Leave every change uncommitted in the working tree. When a task is done, summarise the changed files and suggest a commit message; the owner reviews and commits himself. These rules are also enforced in `.claude/settings.json`.
- **Follow the existing patterns exactly.** Before writing a new file, open the closest existing equivalent (e.g. `Item*` when adding a new entity) and mirror its structure, naming, formatting and level of detail. Do not introduce new libraries, folders, abstractions or architectural styles without asking first.
- Do not add NuGet packages or upgrade versions without asking.
- If a request is ambiguous or would require breaking an existing convention, ask before implementing.
- For anything larger than a small change, propose a plan (files to add or change, per layer) and wait for approval before editing.
- **Keep visibility as low as possible.** Every type and member gets the narrowest access modifier that compiles (`private` > `internal` > `public`). Only make something `public` when another project or a public type genuinely needs it.
- Prefer readability: clear names, early returns, no magic numbers or strings (use `const` and `nameof`).

## Tech stack

.NET 10, C# (latest), Aspire 13 for local orchestration, PostgreSQL via EF Core (Npgsql), Azure Blob Storage for images (Azurite emulator locally), Redis behind HybridCache for read caching, Minimal API, MediatR 14 (CQRS), FluentValidation 12, Scalar (API docs), OpenTelemetry. Admin web is Blazor Web App with Interactive Server render mode and MudBlazor 9.

## Commands

Run from the repo root.

```bash
dotnet build app/OrderPoint.slnx -c Release            # verify every change with this
dotnet ef migrations add <Name> \
  --project app/api/OrderPoint.Infrastructure \
  --startup-project app/api/OrderPoint.Api \
  --output-dir EfCore/Migrations \
  --configuration Release
```

- **The owner keeps the app running** (`aspire run --project app/host/OrderPoint.AppHost`) and verifies changes himself. Never start, stop or restart it; after a change, say what changed and what to check.
- While Aspire runs, the Debug outputs (`bin/Debug`) are locked, so build and run `dotnet ef` with `-c Release` / `--configuration Release`. MSB3021/MSB3027 "file is being used by another process" errors mean a Debug build hit the lock, not a compile error.
- Migrations are applied automatically on API startup (`app.ApplyMigrations()`); do not run `dotnet ef database update`.
- Migration names describe the change as `<Verb>_<What>`: `Add_Item`, `Add_ImageUrl_To_Category`, `Add_Category_Description_And_Status`, `Remove_ShortDescription_From_Item`, `Restrict_Category_Delete`.
- There is no test project yet. Do not add one unless asked.
- "Done" means the build succeeds with no warnings. The AppHost suppresses `ASPIRE010` on purpose (DCP and the dashboard come from NuGet, not the Aspire CLI bundle).
- Secrets live in user secrets, not appsettings. The Api needs `MediatR:LicenseKey`, `Jwt:SigningKey` (at least 32 characters; the API refuses to start without it) and `Admin:Email` + `Admin:Password` (the seeded admin). `appsettings.json` lists these keys with empty values.
- Running the app needs Docker (Aspire starts Postgres on port 59286 and the Azurite blob endpoint on port 59287, both as persistent containers with data volumes; the blob port is fixed because image URLs are stored with it). The design-time `ApplicationDbContextFactory` points at `localhost:5432`; that is fine for `migrations add`, which does not connect.

## Backend conventions

### Domain (`OrderPoint.Domain`)

- Entities are `sealed`, inherit `Entity` (`Id`, `CreatedAtUtc`, `UpdatedAtUtc`), have `private set` properties and a private constructor.
- Creation goes through `public static Result<T> Create(...)` (failures: `Result.Failure<T>(...)`); changes through `public Result Update(...)` (failures: `Result.Failure(...)`). Both validate invariants instead of throwing. `Update` sets `UpdatedAtUtc = DateTimeOffset.UtcNow`.
- IDs are `Guid.CreateVersion7()`, timestamps are `DateTimeOffset.UtcNow`.
- Navigation collections: `private readonly List<T> _items = []` exposed as `IReadOnlyList<T>`.
- Errors live in `Errors/<Entity>Errors.cs` as `static readonly Error` fields built with `Error.NotFound/Validation/Conflict/Unauthorized/Forbidden/Failure` (401/403 are used by `AuthErrors` only), code format `"<Entity>.<Reason>"`. Errors used only inside Domain are `internal`, errors used by handlers are `public`. (`Error.RequestValidation` is reserved for the API's FluentValidation exception handler.)
- Sort options are enums in `Sorting/<Entity>SortBy.cs` (`NameAsc`, `NameDesc`, ..., `CreatedAtUtcDesc`). Other enums go in `Enumerations/`.

### Application (`OrderPoint.Application`)

- One file per use case holding both the message and its handler:
  - `Commands/<Feature>/<Action><Entity>Command.cs`: `public sealed record XCommand(...) : ICommand` or `ICommand<TDto>`, plus `internal sealed class XCommandHandler(...) : ICommandHandler<...>`.
  - `Queries/<Feature>/<Get...>Query.cs`: `public sealed record XQuery(...) : IQuery<TDto>`, plus `internal sealed class XQueryHandler`.
- Use the project's own `ICommand`/`IQuery`/`ICommandHandler`/`IQueryHandler` interfaces from `Mediator/` (all `internal`), never MediatR's `IRequest` directly.
- Handlers return `Result`/`Result<T>`, never throw for business failures. Typical flow: load → `Result.Failure(XErrors.NotFound)` if null → check related entities exist → call domain `Create`/`Update` → propagate failure → repository → `unitOfWork.SaveChangesAsync`.
- Create handlers that return a DTO with navigation data reload the entity after saving (`itemRepository.GetAsync(id)`, which includes `Category`) and map that. If nothing needs loading, map directly (a new category has `itemsCount: 0`).
- Uniqueness rules (e.g. bartender email) are checked in the handler before the domain `Create`/`Update` with `repository.ExistsBy<Field>Async(value)` (e.g. `ExistsByEmailAsync`) and return a `Conflict` error; on update the check only runs when the value changed. A unique index in the EF configuration backs them up. Values are stored as entered (no trimming or lower-casing).
- In the Admin, orders are read-only except for declining an open order (below). The customer app (anonymous) reads `GET api/menu` (`GetMenuQuery`, `Queries/Menu/`: `MenuCategoryDto` with `MenuItemDto`s, only active categories in display order with their active items by name, categories without active items left out; `ICategoryRepository.GetByStatusAsync` includes the items; cached under `menu`), places orders with `POST api/orders` (the validator limits anonymous orders: at most 50 lines, each item once and 1 to 20 pieces, table code up to 10 letters, digits or hyphens) and follows them with `GET api/orders/{id}/tracking` (`GetOrderTrackingQuery` → `OrderTrackingDto`: the order without bartender details; the unguessable id is the permission; cached like `GetOrderQuery`), and can cancel it while it is still Pending with `PUT api/orders/{id}/cancel` (anonymous too, `CancelOrderCommand` → `Order.Cancel()`: status `Cancelled`, `CancelledAtUtc`). Status changes belong to the bartender app and live in the domain: `Order.Accept/Decline/Activate/Complete(bartenderId)` set the status, its `<Status>AtUtc` and `UpdatedAtUtc`. Pending → Accepted (claims the order: sets `BartenderId`) → Active → Completed; Declined from Pending (any bartender, who is recorded as `BartenderId`) or from Accepted (only its bartender); declining always takes a reason for the guest (`Order.DeclineReason`, at most 200 characters, `Order.DeclineReasonIsRequired` when empty). Anything else is `Order.InvalidStatusTransition`, and acting on another bartender's order is `Order.AssignedToAnotherBartender` (both 409). There is no concurrency token (none of the entities has one). Each transition has its own command (`AcceptOrderCommand`, `DeclineOrderCommand`, `ActivateOrderCommand`, `CompleteOrderCommand`, with `Id` and `BartenderId`; each first loads the bartender: `AuthErrors.AccountDeleted` (403) if missing, `AuthErrors.AccountInactive` (403) if inactive, because a deleted or deactivated bartender's access token stays valid for up to 15 minutes; the bartender app's `OrderDetails` then ends the session on either, so the login form shows) and endpoint (`PUT api/orders/{id}/accept|decline|activate|complete`, no body except decline's `{ reason }`, `NoContent`). Two more transitions keep orders from getting stuck: `Order.Release()` (Accepted or Active back to Pending, without bartender, accepted and started times cleared) runs for every open order of a bartender who is deactivated (`UpdateBartenderCommand` and `ChangeBartendersStatusCommand`, through `IOrderRepository.GetOpenByBartendersAsync`), so another bartender picks it up; `Order.DeclineByAdmin(reason)` lets the admin decline any Pending, Accepted or Active order (`DeclineOrderAsAdminCommand`; the decline endpoint is `AdminOrBartender` and picks the command by the caller's role; the bartender, if any, stays recorded). Order lines (`OrderItem`) copy the item's `Name`, `ImageUrl` and price (`UnitPrice`) when the order is placed, so later item changes do not rewrite history (`UpdateItemImageCommand` and `DeleteItemImageCommand` keep the old blob while `IOrderRepository.ExistsByImageUrlAsync` finds a line showing it; the dashboard's and My day's top items still group by item and show its current name); the order total is calculated in the mapper, not stored.
- Items have their own `ItemStatus` (Active/Inactive), but an item in an inactive category counts as inactive too: `Item.IsAvailable` (needs `Category` loaded) is true only when both are Active, and `Order.Create` rejects unavailable items with `OrderErrors.ItemIsUnavailable` (409). Deactivating a category never changes its items' own statuses. The items `status` filter uses the same effective rule (`FilterItems`), and the Admin shows it via `ItemDto.IsActive` (chips, greyscale images); only the edit form shows the item's own status (item details shows an "Inactive" chip next to an inactive category instead).
- Categories have a `DisplayOrder`, the order of the menu in the customer app.
  - **New categories:** they go to the end (`GetMaxDisplayOrderAsync() + 1`). Deleting one leaves a gap, because only the relative order matters.
  - **Reordering:** `ReorderCategoriesCommand` (`PUT api/categories/display-order` with every category id in the new order) renumbers them 1..n. It fails with `CategoryErrors.DisplayOrderMustIncludeAllCategories` unless the list contains every category exactly once.
  - **Admin:** the Categories table has a "Display order" column and Display order ↑/↓ in its sort dropdown (the default stays Created ↓), and category details show it under the ID. Its "Reorder" button (`DataTable.ToolbarActionsContent`) opens `ReorderCategoriesDialog`, a `MudDropContainer` list (loads up to 100 categories). After each drop the dialog reorders its own list and calls `DropContainer.Refresh()`, so the drop zone's internal order can't drift from it.
- Deleting a parent that still has children is blocked in the handler with a `Conflict` error (e.g. `CategoryErrors.CannotDeleteCategoryWithItems`), backed by `DeleteBehavior.Restrict` on the foreign key.
- Bulk commands (`Change<Plural>StatusCommand`, `Delete<Plural>Command` for categories, items and bartenders) are all-or-nothing:
  - They load every id with `GetAsync(IReadOnlyList<Guid> ids)` and return the entity's `NotFound` if any is missing.
  - Blockers are checked for the whole set (`ExistsByCategoriesAsync`, `ExistsByItemsAsync`, `ExistsByBartendersAsync`), returning the single-entity `Conflict` error.
  - They call the domain `ChangeStatus(status)` (a no-op when the status is unchanged) or the repository `Delete` on each, and save once.
  - Image blobs are deleted after saving. Bartender deactivation revokes refresh tokens and releases their open orders, and bartender deletion also deletes the logins.
  - Items have two more bulk commands:
    - `ChangeItemsCategoryCommand` checks that the category exists, then calls `Item.ChangeCategory`.
    - `AdjustItemsPriceCommand` takes a `PriceAdjustmentMode` (`Set`, `ChangeByPercent`, `ChangeByAmount`) and a value. It computes each new price, rounds it to 2 decimals (away from zero) and calls `Item.ChangePrice`. If any price would not be positive, nothing is saved.
- DTOs: `public sealed record XDto(...)` in `Dtos/`. Mapping is manual via extension methods in `Dtos/Mappers/<Entity>Mapper.cs` (`ToXDto()`). No AutoMapper.
- Lists: paged lists return `PaginationDto<T>` (`Get<Plural>Query`). Unpaged lookups, such as autocomplete search, return `IReadOnlyList<T>` (`Search<Plural>Query`).
- Repository interfaces in `Repositories/` (`GetPaginatedAsync`, `SearchAsync`, `GetAsync`, `CreateAsync`, `Delete`, `ExistsAsync`...). Methods that look the entity up by its own id have no suffix (`GetAsync(Guid id)`, `GetAsync(IReadOnlyList<Guid> ids)`, `ICategoryRepository.ExistsAsync(Guid id)`). Methods filtering by anything else say what they filter by in the name, and the parameter is named after it: `IItemRepository.ExistsByCategoryAsync(Guid categoryId)` = "any item in this category", `CountByCategoryAsync(Guid categoryId)`, `IBartenderRepository.ExistsByEmailAsync(string email)`, `IOrderRepository.ExistsByItemAsync(Guid itemId)`, `CountByBartendersAsync(IReadOnlyList<Guid> bartenderIds)`. Saving goes through `IUnitOfWork`, never from a repository.
- Counts of children for a page of entities come from one grouped query that returns a dictionary (`IOrderRepository.CountByItemsAsync(itemIds)` for `GetItemsQuery`, `CountByBartendersAsync(bartenderIds)` for `GetBartendersQuery`), not from including the child collection. A single entity uses the scalar version (`CountByItemAsync(Guid itemId)`). Categories still include `Items` for their counts, which is fine while categories hold few items.
- Dashboard is the one read-model exception: `IDashboardRepository` (no entity of its own) returns DTOs straight from aggregations over orders, because loading entities to sum them would be wasteful. Each dashboard widget has its own query (`Queries/Dashboard/`) and endpoint (`api/dashboard/<widget>?period=Today|Last7Days|Last30Days&timeZone=<IANA id>`; busiest times and live take only `timeZone`) so widgets load in parallel. Periods are calendar based in the viewer's time zone, sent by the Admin and validated with the shared `MustBeValidTimeZone()` rule (`DashboardPeriodRange` computes local midnights with `LocalToUtc`/`UtcToLocal`; buckets are built from local dates, never by adding fixed lengths, so DST days stay correct): A day starts at the business day's start hour, not at midnight, so a night past midnight is one day: the AppHost's `BusinessDayStartHour` (6) reaches the API and the bartender app as `BusinessDay:StartHour`, the API registers it as the singleton `Queries/Dashboard/BusinessDay` (missing = midnight, outside 0-23 stops the API), and handlers pass `businessDay.StartTime` to `DashboardPeriodRange.For` and the dashboard `CacheKeys.For` overloads (`GetLocalToday(now, timeZone, dayStart)` is the business date). Today = since the day start, Last7Days/Last30Days include today (daily buckets start at the day start), and "previous" is the same-length window right before. Revenue and averages count only Completed orders; order counts include every status. Busiest times always cover the last 28 days and group by local weekday and hour on calendar days (`TimeSpan.Zero`), since its axes are clock hours. The bartender app's "My shift" uses the same repository: `GetShiftQuery` (`Queries/Shift/`, `GET api/shift?timeZone=`, Bartender policy, not cached) returns `ShiftDto(PendingCount, MyOpenCount, CompletedCount, AverageServiceMinutes)`: every pending order, the bartender's accepted and active ones, and the ones they completed since the day start (by `CompletedAtUtc`, so an order placed before it still counts) with the dashboard's service time (placed → completed). `GetShiftDayQuery` (`GET api/shift/day?timeZone=`, same rules) returns `ShiftDayDto(Revenue, ItemsCount, Hours, TopItems)` for the orders the bartender completed since the day start: total, pieces, `ShiftHourDto(Hour, CompletedCount)` per local hour from the first hour with a completed order to the current hour, counted from the day start (22, 23, 0, 1 for a night) (quiet hours as 0; empty without completed orders), and the top 3 items (`TopItemDto`); the repository methods are `GetCompletedOrdersByBartenderAsync` and `GetCompletedItemsByBartenderAsync`.
- MediatR handlers are registered by assembly scan; no manual registration needed.

### Infrastructure (`OrderPoint.Infrastructure`)

- `ApplicationDbContext` implements `IUnitOfWork`; `DbSet`s are `internal`.
- One `IEntityTypeConfiguration<T>` per entity in `EfCore/EntityTypeConfiguration/` (table name, `ValueGeneratedNever()` on Id, `HasMaxLength`, `IsRequired`, relationships). Each property is configured as `builder` / `.Property(...)` / `...` on separate lines. Relationships use `.OnDelete(DeleteBehavior.Restrict)`. Picked up by assembly scan. Money columns (`Item.Price`, `OrderItem.UnitPrice`) use `HasPrecision(10, 2)`. The only database-generated value is `Order.Number` (`UseIdentityAlwaysColumn()` plus a unique index), the human-readable order number.
- Repositories are `internal sealed class <Entity>EfCoreRepository(ApplicationDbContext dbContext)` in `EfCore/Repositories/`, using private static `Search<X>`/`Filter<X>`/`Sort<X>` helpers for paginated queries (search is case-insensitive via `ToLower().Contains`; default sort `CreatedAtUtc` descending; unpaged search sorts by name ascending). `Sort<X>` builds an `IOrderedQueryable` and always ends with `.ThenBy(x => x.Id)` so paging is stable when sort values tie. Read-only queries (`GetPaginatedAsync`, `SearchAsync`) use `AsNoTracking()`; `GetAsync` stays tracked because commands update and delete what it returns, and it includes the navigations its DTO needs. Register in `InfrastructureModule`.

### API (`OrderPoint.Api`)

- `Program.cs` pipeline order: `ApplyMigrations` → `SeedAdminAsync` → `UseExceptionHandler` (first middleware) → `UseHttpsRedirection` → `UseCors` → `UseAuthentication` → `UseAuthorization` → endpoint, hub and docs mapping. `launchSettings.json` URLs never contain a path (Kestrel refuses them); use `launchUrl` instead.
- CORS: one policy that allows only the origins in `Cors:AllowedOrigins` (empty by default in `appsettings.json`), any header, and GET/POST/PUT/DELETE. Nothing needs CORS today (the Admin, the bartender app and the customer app are Blazor Server and call the API from their servers, Scalar is same-origin); add an origin only for a client that calls the API from the browser (e.g. a WebAssembly or JS client). Never go back to `AllowAnyOrigin`.
- One endpoint per file in `Endpoints/<Feature>/<Action><Entity>Endpoint.cs`: `internal sealed class XEndpoint : IEndpoint`, discovered automatically.
- Request and response records (`internal sealed record`) are declared in the same file above the endpoint; the FluentValidation validator is a nested `internal sealed class XRequestValidator` inside the endpoint class (auto-registered). Every endpoint that takes a body or query string has a request record and a validator.
- Query-string input is bound into a request record with `[AsParameters] XRequest request`; its constructor parameters carry `[FromQuery]` (see `GetItemsEndpoint`, `SearchCategoriesEndpoint`). Paged lists validate `PageNumber > 0` and `PageSize` between 1 and 100; search text is at most 100 characters (a search that cannot match returns no results, not an error); required search text uses `NotEmpty()` (also rejects whitespace). Route values (`{id:guid}`) stay as `[FromRoute]` parameters.
- `MapEndpoint` uses route `api/<plural>`, `api/<plural>/{id:guid}`, `api/<plural>/search?searchQuery=...` (unpaged lookup), plus `.WithName("<Action><Entity>")`, `.WithTags("<Plural>")` and, for every Admin endpoint, `.RequireAuthorization(AuthorizationPolicies.Admin)` as the last call. Endpoints without `RequireAuthorization` are anonymous (auth endpoints, the customer app's `GET api/menu`, `POST api/orders`, `GET api/orders/{id}/tracking` and `PUT api/orders/{id}/cancel`, health checks, API docs), so never forget it on a new Admin endpoint. Bartender app endpoints use `AuthorizationPolicies.Bartender` (or `AdminOrBartender` when the Admin calls them too) instead and take the bartender id from the token (`user.GetUserId()`; a bartender's user id is the `Bartender.Id`).
- API documentation (Scalar at `/scalar`, document at `/openapi/v1.json`). Every endpoint and record is documented:
  - **Endpoint chain:** after `.WithTags(...)` comes `.WithSummary("Short imperative")`, then `.WithDescription("""...""")` (Markdown: what it does, the rules, and one bullet per domain error, e.g. ``- `409 Category.CannotDeleteCategoryWithItems`: the category still has items``), then `.ProducesProblem(StatusCodes.Status404NotFound)` / `409` / `401` / `403` for the errors the handler can return. 400, the auth 401/403 and 500 are added automatically.
  - **Records:** request and response records (Api) and DTOs (Application) get `/// <summary>` plus one `/// <param name="Field">` per positional parameter, all of them (a partial set warns with CS1573). Escape `<`/`>` as `&lt;`/`&gt;`. Api and Application set `GenerateDocumentationFile` (CS1591 suppressed); the OpenAPI source generator picks the comments up, including from the referenced Application project.
  - **Transformers** live in `OpenApi/`, registered by `AddApiDocumentation()` and mapped by `MapApiDocumentation()`. Never edit the generated document by hand.

    | Transformer | What it does |
    | --- | --- |
    | `DocumentInfoTransformer` | Title, the Markdown guide in `ApiGuide.cs` (authentication, envelope, pagination, errors, conventions), tag descriptions, `x-tagGroups`, the bearer scheme |
    | `SecurityTransformer` | The bearer requirement, a role note (the roles its policy allows, read from `AuthorizationOptions`), and 401/403, only on endpoints with `RequireAuthorization` |
    | `ResponsesTransformer` | 400 for endpoints with a body or query parameters; clear descriptions for the standard status codes |
    | `ProblemDetailsSchemaTransformer` | The `errors` array on `ProblemDetails` |
    | `EnumSchemaTransformer` | Enum values, names and `x-enum-varnames` |
    | `NumberSchemaTransformer` | Drops the "number or string" noise |
    | `ValidationTransformer` + `ValidationRules` | Copies unconditional FluentValidation rules (NotEmpty, lengths, comparisons, ranges, email) into body schemas and `[AsParameters]` query parameters; `When` and `Must` rules cannot be expressed in a schema, so describe them in the endpoint's `.WithDescription` |
  - **Shared 500:** `MapEndpoints` maps every endpoint in an empty group with `.ProducesProblem(500)`, which also registers the shared `ProblemDetails` schema.
- `private static async Task<Results<..., ProblemHttpResult>> HandleAsync(...)` with explicit `[FromBody]`/`[FromRoute]`/`[FromQuery]`/`[FromServices]` attributes and a `CancellationToken`.
- Flow: `await validator.ValidateAndThrowAsync(request, ct)` → build command/query → `sender.Send` → `result.IsSuccess ? TypedResults.X(...) : result.ToProblemDetails()`.
- Responses wrap payloads as `{ Data }`: create → `CreatedAtRoute` to the Get route, update/delete → `NoContent`, get → `Ok`.
- Bulk endpoints: `PUT api/<plural>/status` with `{ ids, status }` and `POST api/<plural>/delete` with `{ ids }`, both returning `NoContent`. Their validators use the shared `RuleFor(request => request.Ids).MustBeValidIds()` (`Extensions/IdsValidationExtensions.cs`: 1 to 100 ids, no empty id, no duplicates). Items also have `PUT api/items/category` with `{ ids, categoryId }` and `PUT api/items/price` with `{ ids, mode, value }`. The price value must be positive for `Set`, non-zero otherwise, and above -100 for `ChangeByPercent`.
- Errors are ProblemDetails with an `errors` array; status mapping lives in `Extensions/ResultExtensions.cs`. Exception handlers in `Exceptions/` (registered in `Program.cs`, in order): `RequestValidationExceptionHandler` (FluentValidation → 400), `BadHttpRequestExceptionHandler` (missing/unparsable parameters or malformed JSON → 400; `ThrowOnBadRequest` is on so this applies in every environment), `GlobalExceptionHandler` (logs the exception, → 500 without exposing exception details). In .NET 10 the exception middleware does not log exceptions a handler reports as handled, so any new handler for unexpected errors must log itself.

### Caching

- Reads are cached with `HybridCache` (`AddHybridCache` in `InfrastructureModule`: 5 minutes in memory, 30 minutes in Redis). The API's `builder.AddRedisDistributedCache("cache")` registers the `IDistributedCache` HybridCache uses as its second level. Redis has no data volume, so every run starts empty. `BacklogPolicy.FailFast` makes Redis calls fail at once while it is down, so reads fall back to memory and the database instead of waiting for a timeout. Its health check (`StackExchange.Redis`, shown as "Cache") reports `Degraded` through `ReportHealthCheckFailureAsDegraded`.
- **Reads:** the query handler wraps its work in `cache.GetOrCreateAsync(CacheKeys.For(query), query, Get<X>Async, tags: [CacheTags.<Feature>], cancellationToken: ...)`. The old `Handle` body lives in `private async ValueTask<TDto> Get<X>Async(query, ct)`, and `Handle` turns the DTO into the `Result` (a not-found is cached as `null` and mapped to the `NotFound` error). The DTO is cached, never `Result<T>` (not serializable). Cached: get, list and search for categories, items, bartenders and orders, order tracking, the guests' menu, and every dashboard widget except live. Not cached: live, shift, account, auth, health.
- **Keys:** `Caching/CacheKeys.For(<query>)`, one overload per query, `<feature>:<id>`, `<feature>:page:<every parameter>` and `<feature>:search:<text>`, free text always last. Dashboard keys hold the period, the time zone id and the viewer's local date, so periods move on at the day start.
- **Writes:** a command whose change shows up in cached reads implements `Mediator/ICacheInvalidatingCommand` explicitly (`IReadOnlyList<string> ICacheInvalidatingCommand.InvalidatedCacheTags => CacheTags.<X>Changes;`), and `Mediator/CacheInvalidationBehavior` (after `TelemetryBehavior`) calls `RemoveByTagAsync` once the command succeeds, with `CancellationToken.None` so a caller who left can't keep stale data. The groups in `Caching/CacheTags` follow what each DTO shows: `CategoryChanges` (categories, items, dashboard, menu), `ItemChanges` (items, categories, orders, dashboard, menu), `BartenderChanges` (bartenders, orders, dashboard), `OrderChanges` (orders, items, bartenders, dashboard). Auth, account and `ResetBartenderPasswordCommand` change nothing cached.
- **New use cases:** a new query gets a `CacheKeys.For` overload and the tag of its feature; a new command that changes something a cached DTO shows implements `ICacheInvalidatingCommand`, and a new DTO field that comes from another feature means adding that feature's changes to its group. The order status changes (bartender app) use `OrderChanges`.

### Real time

- The staff hub, `Api/Hubs/OrdersHub` (`builder.Services.AddSignalR()`, `app.MapHub<OrdersHub>("hubs/orders").RequireAuthorization(AuthorizationPolicies.AdminOrBartender)`). Clients only listen; the hub has no methods. The Admin and the bartender app are Blazor Server, so they connect with the .NET client from the server, which sends the bearer token as a header (no `access_token` query handling, no CORS).
- Its messages are `OrdersChanged` (`OrdersHub.OrdersChangedMethod`) and `MenuChanged` (`MenuChangedMethod`), both without arguments: clients reload what they show.
- **Sending:** the commands that place an order or change its status (`CreateOrderCommand`, `Accept/Decline/Activate/CompleteOrderCommand`, `DeclineOrderAsAdminCommand`, `CancelOrderCommand`) implement the marker `Mediator/IOrderNotifyingCommand`. `Mediator/OrderNotificationBehavior` (registered between `TelemetryBehavior` and `CacheInvalidationBehavior`, so it runs after the cache is cleared and a reload is never stale) calls `Notifications/IOrderNotifier` once such a command succeeds. `Api/Hubs/SignalROrderNotifier` (singleton) sends to all clients and logs a warning instead of failing when sending fails, because the change is already saved.
- A new command that changes what the apps show about orders implements `IOrderNotifyingCommand` too, and its handler adds every order it changed to the scoped `Notifications/ChangedOrders` after saving (a release can change several, known only once the handler ran; `CreateOrderCommand` adds none, nobody can follow an order before it exists). The bartender commands that can deactivate (`UpdateBartenderCommand`, `ChangeBartendersStatusCommand`) are order-notifying too, because they release orders.
- **Guests:** a second hub, `Api/Hubs/OrderTrackingHub` (`app.MapHub<OrderTrackingHub>("hubs/order-tracking")`, anonymous), for the customer app. Its one method `TrackOrder(orderId)` (`TrackOrderMethod`) adds the connection to the group `order:<id>`; clients call it for every order they follow and again after a reconnect (groups are lost). `IOrderNotifier.NotifyOrdersChangedAsync(changedOrderIds)` (called by `OrderNotificationBehavior` with `ChangedOrders.OrderIds`) sends `OrdersChanged` to the staff hub and `OrderChanged` (no arguments, `OrderChangedMethod`) to the groups of the changed orders, so a guest only hears about their own orders.
- **Menu:** every item and category command (17, including status, price, image and menu order) implements the marker `Mediator/IMenuNotifyingCommand`; `Mediator/MenuNotificationBehavior` (registered right after `OrderNotificationBehavior`, also outside `CacheInvalidationBehavior`, so a reload is never stale) calls `Notifications/IMenuNotifier` once such a command succeeds, and `Api/Hubs/SignalRMenuNotifier` (singleton, logs a warning instead of failing) sends `MenuChanged` to every connection of both hubs, since anyone may be looking at the menu. A new command that changes an item or a category implements the marker too.
- **Receiving:** `OrderPoint.Shared/Orders/Services/OrdersHubService` (scoped, one connection per circuit, package `Microsoft.AspNetCore.SignalR.Client`) connects to `<api>/hubs/orders`. WebSockets bypass the service discovery HttpClient, so the URL comes from Aspire's `services:order-point-api:https:0` (else `http:0`); the token comes from `AuthService.GetAccessTokenAsync`. The first connect and automatic reconnects retry after 0, 2, 10 and then every 30 s. It raises `OrdersChanged` and `MenuChanged` on their messages and both after a reconnect (messages sent while down are lost), and `StateChanged` with `State` for a connection indicator. `MainLayout` starts it after sign-in (not awaited) and stops it on sign-out; the circuit scope disposes it.
- **Admin pages:** everything that shows order data subscribes to `OrdersChanged` (and everything that shows items or categories to `MenuChanged`: `CategoriesPage` (table and top 5, selection kept), `ItemsPage` (grid and spotlight), `CategoryDetailsDialog` (its items) and `ItemDetailsDialog`, which refetches the item into `CurrentItem` because the dialog provider resets parameters) in `OnInitialized(Async)`, unsubscribes in `Dispose`, and reloads silently: `OrdersPage` (status counts + the current timeline page, filters kept), `DashboardPage` (every section; the live panel keeps its 30 s timer too), `ItemsPage` and `BartendersPage` (the current page, for the order counts; not the spotlight or team strip), `BartenderOrdersList` (`BartenderOrdersDialog`), `BartenderOrdersSummary` (the expanded bartender row's last order), `ItemDetailsDialog` (orders count and list) and `OrderDetailsDialog` (refetches the order into `CurrentOrder`, because the dialog provider resets parameters; for an open order it has a "Decline order" button on the left of the actions, which asks in `Orders/Dialogs/DeclineOrderDialog` (order summary, "This action cannot be undone. The guest sees the order as declined, with your reason.", and the shared `DeclineReasonField`: quick-pick chips from `OrderPoint.Shared/Constants/DeclineReasons` that fill the required "Reason for the guest" field, 200 characters, clearable; the dialog returns a `DeclineOrderRequest`, and a declined order shows a "Decline reason" row) and calls `PUT api/orders/{id}/decline` itself, since the dialog opens from several pages that all reload on `OrdersChanged`). Load methods take `bool isLiveUpdate = false`: a live update shows no skeleton and keeps the bulk selection (re-pointed by id at the reloaded records); on the dashboard `OnPeriodChangedAsync` sets the loading flags itself. `DataAccordion` keys its panels with `GetItemKey` (the id), so a live reload keeps an expanded row open.
- **New orders:** `NewOrdersTracker` (`OrderPoint.Shared/Orders/Services`, one per list, not DI) marks orders created after the list's previous load started as new for 10 s; the Orders timeline (`DataTimeline.IsItemNew`) and the dashboard's `RecentOrdersList` wrap them in `NewItemHighlight` (tinted background that fades over 3 s) and show a filled "New" chip (next to the status chip on tickets, instead of it in Recent orders, so the row shows "New" first and then its status). `Orders/Services/NewOrderToastService` (scoped, driven by `MainLayout`: baseline after sign-in, `CheckAsync` on every `OrdersChanged`) compares the 5 newest order numbers with the last one it saw and shows a snackbar on every page: "New order #128 · Table 4 · €23.50" (View opens `OrderDetailsDialog`) or "3 new orders" (View opens `/orders`); the action button uses `ActionVariant = Variant.Text`, because the outlined snackbars would give it a border.
- **Changing numbers:** live numbers (status counts, KPI values, Right now values, top items and leaderboard numbers) render through `RollingNumber` (`OrderPoint.Shared/Components`, generic `Value` for the direction + formatted `Text`): when the value changes the old text slides out and the new one in, up when it grew, down when it shrank; never on first render, off under `prefers-reduced-motion`. Use it for any new number that live updates change.

### Images

- Images live in the blob container `images` and the entity stores the full public URL in `ImageUrl` (UI uses it directly). The API gets a `BlobContainerClient` from `builder.AddAzureBlobContainerClient("images")` and `app.CreateImageContainer()` makes the container publicly readable at startup.
- `IImageStorage` (Application `Storage/`, implemented by Infrastructure `Storage/BlobImageStorage`): `UploadAsync(stream, contentType, folder)` stores `<folder>/<guid>` and returns the URL; `DeleteAsync(imageUrl)`. A new upload always gets a new name, so browsers never show a cached old image.
- Images are not part of create/update. Each entity with an image gets `PUT api/<plural>/{id}/image` (multipart form field `image`, `[FromForm]` request record, `.DisableAntiforgery()`) and `DELETE api/<plural>/{id}/image`, backed by `Update<Entity>ImageCommand`/`Delete<Entity>ImageCommand` and domain `SetImage(url)`/`RemoveImage()`. Replacing an image deletes the old blob after saving; deleting the entity deletes its blob. An item's old blob stays while an order line still shows it. Limits: JPEG, PNG or WebP, at most 2 MB, checked by the API validators through the shared `RuleFor(request => request.Image).MustBeValidImage()` (`Extensions/ImageValidationExtensions.cs`) and by the Admin `ImageUploadField`.
- Admin: dialogs use the shared `ImageUploadField` (upload button, optional remove, inline error) which reads the file into an `ImageFileDto`; the preview paper shows it via `ImageFileDto.ToDataUrl()`. The request carries it as `[JsonIgnore] Image` (update also `[JsonIgnore] RemoveImage`), and the page sends create/update and then the image call inside one `ApiService.ExecuteAsync` (see `CategoriesPage`).
- Categories, Items and Bartenders all have uploads (blob folders `categories/`, `items/`, `bartenders/`), and so does the admin account (`users/`, `ApplicationUser.ImageUrl`, `PUT`/`DELETE api/account/image`). Bartenders without an image show coloured initials in `BartenderAvatar` (text size follows the avatar `Size`). Item cards use the shared `ItemCardContent` (`OrderPoint.Shared/Items/Components`, plain-value parameters so each app keeps its own `ItemDto`; the caller wraps it in a `MudCard`; `IsDescriptionClamped="false"` shows the whole description; `Portion` and `OrdersCount` are optional (null hides them; " · " only appears between both) and `ShowsStatus="false"` hides the status chip, all three for guests), used by the Admin's `ItemsPage` grid and the bartender app's `MenuItemPage`. Its top is `ItemCardImage`: the image at a fixed height, uncropped, centred over a blurred, faded copy of itself that fills the card's top area (so the background matches the image's colours), or the centred placeholder in an area of the same height. Below it the card reads like a menu: muted category (16px thumbnail and name) with the small Active/Inactive chip (20px, caption-sized) at the other end of that row, name (h6), description clamped to 2 lines, and a bottom row (`mt-auto`, so footers line up) with the price on the left and "portion · n orders" on the right. Missing images fall back to `ImageUrls.Placeholder` (`OrderPoint.Shared/Constants/ImageUrls.cs`): `Src="@(x.ImageUrl ?? ImageUrls.Placeholder)"`. Small fixed-size thumbnails use `MudImage` with `ObjectFit.Cover` so photos are cropped, not stretched; never `MudCardMedia` inside a list row (it defaults to 300px tall). Every item and category picture has soft corners from `OrderPoint.Shared/Constants/ImageStyles`: `Style="@ImageStyles.Rounded"` (the theme radius) from 32 px up, `@ImageStyles.RoundedSmall` (4px) for thumbnails up to 24 px, so they don't turn into circles; combine it with other styles (`$"{ImageStyles.Rounded} flex-shrink: 0;"`), never hand-write the radius.
- Orders have no image; `OrderAvatar` (`OrderPoint.Shared/Orders/Components`) shows `#<Number>` (h6) in a rounded grey tile (filled `MudAvatar` that stretches to the height of the text beside it, at least 72px wide so up to 4 digits line up). Every order list row uses the same layout: tile, `Spacing="3"`, "Table T11" over the time, spacer, status chip, total. The order details dialog shows the number as plain text. Orders timeline tickets are split in two by a vertical divider: on the left (45%) the header (tile, table and time, status chip), the note, and the bartender with the total at the bottom; on the right each order line with a 32px image, "2× name" and the line total. Below the note a declined ticket says "Declined: <reason>" and a cancelled one "Cancelled by the guest" (status icon, secondary text).

### Authentication

- ASP.NET Core Identity, but only its user store: `UserManager` with `UserOnlyStore` on the plain `ApplicationDbContext` (password hashing, lockout, unique email, security stamp). No `SignInManager`, `MapIdentityApi`, Identity UI, cookies, claims, external logins, 2FA or Identity roles. Tables: `Users` (Infrastructure `Identity/ApplicationUser`, fully configured in `ApplicationUserTypeConfiguration`, unused Identity columns ignored) and `RefreshTokens`.
- Two roles in `UserRole` (a column on the user): `Admin` (only seeded at startup from `Admin:Email`/`Admin:Password` when that email does not exist yet) and `Bartender`. A bartender's user has the same `Id` as the `Bartender` row; creating a bartender creates the login (temporary password, `MustChangePassword = true`), changing the email updates it, deactivating revokes refresh tokens, deleting deletes it. A forgotten password is reset by the admin (`PUT api/bartenders/{id}/password`, "Reset password" button in the bartender's expanded row): a new temporary password, `MustChangePassword = true` again, lockout lifted, refresh tokens revoked.
- Application talks to Identity only through `Identity/IIdentityService` and `Identity/ITokenService` (implemented in Infrastructure `Identity/`). The user store (`ApplicationUserStore`) runs with `AutoSaveChanges = false`, so user and token changes are saved by the handler's `IUnitOfWork` together with everything else; its `UpdateAsync` only marks the user modified, because the base store re-attaches the user, which breaks the concurrency check when one request makes several user updates before saving.
- Tokens: JWT access token (HS256, 15 minutes, claims `sub`, `email`, `role`) and a random refresh token (7 days, only its SHA-256 hash stored, replaced on every refresh). Lifetimes, issuer and audience are in `appsettings.json` (`Jwt`), the key in user secrets. `ClockSkew` is zero. `AuthTokensDto` (login, refresh, password change) carries `UserId` (a bartender's is their `Bartender.Id`), `Email` and `Role` next to the tokens.
- Endpoints (anonymous): `POST api/auth/login` (`email`, `password`, `role`), `POST api/auth/initial-password` (first login only), `POST api/auth/refresh`, `POST api/auth/logout`. The account endpoints take the user id from the token (`ClaimsPrincipal.GetUserId()`, `Extensions/ClaimsPrincipalExtensions.cs`). `PUT api/account/password` changes the password; a wrong current password is `AuthErrors.InvalidCurrentPassword` (400, not 401, so the Admin doesn't treat it as an expired session). It then revokes every refresh token and returns a new token pair, which the Admin stores with `AuthService.ReplaceTokensAsync`. `POST api/account/sign-out-everywhere` revokes every refresh token, and the Admin then calls `AuthService.EndSessionAsync`. `GET api/account` returns `AccountDto(Email, ImageUrl, FirstName, LastName, PhoneNumber)`; for a bartender `ImageUrl` is the `Bartender` photo the admin set and the other three come from the `Bartender` too (all `null` for the admin); a deleted bartender gets `AuthErrors.AccountDeleted` (403), and the shared `AccountService` then ends the session, so the bartender app shows the login form. These three use `AdminOrBartender`; the profile image upload and removal (`PUT`/`DELETE api/account/image`) stay Admin-only. The admin email cannot be changed, because `SeedAdminAsync` would recreate the admin from `Admin:Email`. The Admin `Account/` feature folder has `AccountPage` (`/account`: a profile card with avatar, email and role, and a settings card with sections Profile image, Appearance (Light | Dark toggle group, `DarkModeService`), Password, Sessions, Sign out); the rest of the feature (`AccountApiClient`, `AccountDto`, `ChangePasswordRequest`, `AccountService`) and its dialogs `ChangePasswordDialog`, `SignOutEverywhereDialog` and `SignOutDialog` live in `OrderPoint.Shared/Account` (signing out asks for confirmation). Each app sends its own role; a user of the other role gets `InvalidCredentials`, exactly like a wrong password. 5 failed attempts lock an account for 5 minutes. A bartender with `MustChangePassword` gets `PasswordChangeRequired` (403) and must use `initial-password`, which works only while the flag is set (the shared `LoginForm` handles it: `AuthService.LoginAsync` returns true for `Auth.PasswordChangeRequired` (`ApiException.HasErrorCode`), and the form switches to a "choose your password" step that posts the temporary password just typed plus the new one and signs in with the returned tokens); an inactive bartender gets `AccountInactive`.
- Authorization: policy `AuthorizationPolicies.Admin` (role `Admin`) on every Admin endpoint, `AuthorizationPolicies.Bartender` (role `Bartender`) on the bartender app's endpoints, and `AuthorizationPolicies.AdminOrBartender` on the ones both apps call (`GET api/orders`, `GET api/orders/{id}`, `PUT api/orders/{id}/decline`, `GET api/items`, `GET api/items/{id}`, `GET api/categories` and `GET api/categories/{id}` (the bartender app's menu), `PUT api/items/status` and `PUT api/categories/status` (the bartender app takes things off the menu when they run out), `GET api/account`, `PUT api/account/password`, `POST api/account/sign-out-everywhere`). Scalar sends a pasted bearer token (`SecurityTransformer`; the token is remembered with persistent authentication).
- Admin: the `Auth/` feature folder lives in `OrderPoint.Shared`, so the bartender app reuses it. `AuthService` (one per circuit) keeps the tokens in `ProtectedLocalStorage`, refreshes one minute before expiry under a lock (parallel calls refresh once) and raises `SessionChanged`. `AccessTokenHandler` on every typed API client attaches the token; it reaches the circuit's `AuthService` through `CircuitServicesAccessor` + `ServicesAccessorCircuitHandler` (the documented pattern, since `IHttpClientFactory` handlers live in another DI scope). `AuthApiClient` is registered without the handler. `MainLayout` is the gate: it renders nothing until the session is loaded, then `LoginForm` instead of the page when signed out, so no page needs `[Authorize]`. `LoginForm` takes the app's `Role` (sent with the login, and picking the brand panel's tagline and three feature lines) and `AppName` ("Welcome back. Sign in to Admin web." and the footer). It is a split screen: from 960 px (`MudHidden` `SmAndDown`) a brand panel on the left (logo, tagline in h3, features as outlined icon tiles with title and line, "OrderPoint · Admin web" at the bottom; a faint text-colour tint and a `lines-default` border, since the theme is monochrome) and the form on the right (max 400px, h1 "Sign in" or "Choose your password", spinner on the button while signing in, and for bartenders "Forgot your password? Ask the admin to reset it."); below 960 px the panel becomes a small logo header above the form: `<LoginForm Role="UserRole.Admin" AppName="Admin web" />`. The drawer's last section, System, holds Health and Account (person icon, opens `/account`), plain nav links like the rest. The profile image is shown only on the account page; it comes from the scoped `AccountService`, which `MainLayout` loads after sign-in and clears on sign-out, and the account page uploads and removes it with `ImageUploadField` (removing asks first in `Account/Dialogs/RemoveAccountImageDialog`). Sign out lives on the account page as its last section. The drawer toggle tab sits at `bottom: 72px`. There is no hamburger button: a round chevron tab on the drawer's edge toggles it; it is a fixed div placed directly after `MudDrawer`, because MudBlazor gives such a div a left margin equal to the drawer width (see `MainLayout.razor.cs`). Prerendering is off (`App.razor`) because browser storage is readable only once the circuit is connected. `App.razor.cs` picks the render mode per request: interactive server for every page, except pages marked `[ExcludeFromInteractiveRouting]`, which render statically. That is only `/Error`: after the exception handler re-executes, the interactive router would render the failing URL again. `/Error` uses `ErrorLayout` (just the theme, because `MainLayout` needs browser storage). `/not-found` (the router's `NotFoundPage` and the status-code re-execute target) and `/Error` both show the shared `StatusMessage` (icon, h1 title, text, caption, and a button back to "/" whose `ButtonText`/`ButtonIcon` each app passes: "Back to dashboard" in the Admin, "Back to orders" in the bartender app). When a refresh fails, calls throw `SessionExpiredException`, which `ApiService` ignores silently, and the login form says the session expired. Lost connections show `ReconnectModal` (`OrderPoint.Shared/Layout`) instead of Blazor's built-in dialog (which ignores the theme): a `<dialog id="components-reconnect-modal">` rendered statically in `App.razor` after `Routes`, the .NET 10 template's pattern. Blazor sets its state classes (`components-reconnect-show`, `-retrying`, `-failed`, `-paused`, `-resume-failed`) and raises `components-reconnect-state-changed`; `ReconnectModal.razor.js` opens/closes it (Esc can't dismiss it) and wires Retry and Resume, and `ReconnectModal.razor.css` styles it with MudBlazor palette variables, so it follows dark mode. The library's scoped CSS (`ReconnectModal`, `RollingNumber`, `NewItemHighlight`) is the only custom CSS besides `App.razor`'s `<style>` block (`OrderPoint.Admin.styles.css`, linked in `App.razor`, imports it from the library).

### Observability

Everything goes to the Aspire dashboard over OTLP (structured logs, traces, metrics). An Admin page load shows as one trace: Admin → API → MediatR span → SQL.

- **ServiceDefaults** (`ServiceDefaultsExtensions`, only `AddServiceDefaults` and `MapDefaultEndpoints` are public):
  - **Instrumentation:** OpenTelemetry for ASP.NET Core, HttpClient and runtime, plus every `OrderPoint.*` source and meter and Blazor Server's built-in sources and meters (`Microsoft.AspNetCore.Components*`: navigation, events, circuits, rendering). Requests to `/health` and `/alive` are not traced.
  - **Resilience:** the HttpClient handler retries GET only (`DisableForUnsafeHttpMethods`), so a timed-out POST/PUT/DELETE never runs twice.
  - **Health endpoints:** `/health` (ready, every check) and `/alive` (only the `live` "self" check), Development only; Aspire's `WithHttpHealthCheck` uses `/health`.
  - **Health check timeout:** every check without its own timeout gets 5 s (a `PostConfigure<HealthCheckServiceOptions>`, so it also covers the Aspire integrations' checks). A stopped container behind Aspire's proxy hangs instead of refusing the connection; without the timeout `GET api/health` waited until the Admin gave up and showed the API itself as unreachable. Keep it well under the Admin's 10 s attempt timeout. `GetHealthEndpoint` turns the resulting `OperationCanceledException` into a readable "No response in time" error, and Redis' `RedisConnectionException` (a long diagnostic dump) into "Can't connect to Redis; it may be stopped...".
  - **Rule:** ServiceDefaults knows nothing about a specific database or storage; their telemetry and health checks come from the Aspire client integrations in the API.
- **Database:** Infrastructure registers `ApplicationDbContext` as usual; the API's `builder.EnrichNpgsqlDbContext<ApplicationDbContext>()` (package `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL`) adds its health check, Npgsql traces and metrics, and retries on transient errors (so never open a manual transaction without the execution strategy). `AddAzureBlobContainerClient` does the same for blobs. SQL shows up as trace spans, so `Microsoft.EntityFrameworkCore.Database.Command` logs only warnings.
- **Application telemetry** (`Telemetry/ApplicationTelemetry`, singleton, source and meter `OrderPoint.Application`):
  - `Mediator/TelemetryBehavior` (registered with `AddOpenBehavior`) wraps every command and query: a span named after the request (tags `orderpoint.request.name`, `orderpoint.request.type`, `error.type` = error code on failure, error status), the `orderpoint.request.duration` histogram (seconds, same tags), and a log: Information on success, Warning with the error code on failure. It never logs the request itself (passwords). Exceptions only mark the span and the metric; `GlobalExceptionHandler` logs them.
  - Business metrics: `orderpoint.orders.placed`, `orderpoint.orders.value` (EUR) from `CreateOrderCommand`, `orderpoint.auth.logins` (tags `orderpoint.user.role`, `error.type`) from `LoginCommand`. Add new instruments to `ApplicationTelemetry` with an `orderpoint.` name and a `Record...` method.
- **Event logs:** handlers whose outcome matters later (sign-ins, password changes and resets, signing out everywhere, bartender create/status/delete, order placed, order status changes, deletes, bulk status, price and category changes) log it with source-generated `[LoggerMessage]` methods (`private partial void LogX(...)` on a `partial` handler that takes `ILogger<THandler> logger`). Message templates use named placeholders (`{BartenderId}`, `{Email}`, `{ItemCount}`) so they become structured attributes; never log passwords or tokens. Queries and plain edits rely on the pipeline log. `RequestValidationExceptionHandler` logs failed validations (method, path, error codes), since they never reach MediatR.
- **Health in the Admin:** `GET api/health` (Admin policy, tag Health) runs `HealthCheckService` directly (a host concern, not a use case, so no MediatR) and returns each check with a display name (`self` → API, `ApplicationDbContext` → Database, `Azure_BlobContainerClient` → Storage, `StackExchange.Redis` → Cache, `pgweb` → Database browser, `storage-blobs-explorer` → Storage browser, `redisinsight` → Cache browser, `order-point-bartender` → Bartender web, `order-point-customer` → Customer web; add new checks to its `DisplayNames`, and the Admin card's title must equal that name). The Admin's `Health/` feature: the scoped `HealthService` calls it without `ApiService` (an unreachable API is a red result, not a snackbar), replaces the API check's duration with the Admin's round trip, and raises `Changed`; `MainLayout` checks after sign-in and every 30 s (`PeriodicTimer`). `HealthStatusIndicator`, the last item in the app bar (a text button with the coloured status icon; hovering slides the summary, e.g. "All systems operational", out to the left of the icon via a `max-width` transition toggled by `@onmouseenter`/`@onmouseleave`; no tooltip; links to the page), and `HealthPage` (`/system`, titled "Health", the Health link under System in the drawer: `HealthSummary` banner, one `HealthCheckCard` per component in three sections, "Core services" (API, Database, Storage, Cache), "Apps" (Bartender web and Customer web: the API's `AddDevToolHealthCheck("order-point-bartender")` and `("order-point-customer")` gets its `/`, Degraded when down) and "Developer tools" (Database browser, Storage browser, Cache browser), 3 cards per row, each titled with the check's name over the product (e.g. "Database browser" over "pgweb"), skeletons, a Refresh button that shows a spinner and "Checking..." while a check runs). When the API can't be reached or answers with an error, its card shows only a short description ("Not reachable from the Admin", "Responded with an error"); the exception goes to the Admin's log, not the page share it. Status colours, icons and texts come from `HealthStatusExtensions` (null = unknown, e.g. while the API is unreachable).
- **AppHost:** the API resource has an "API reference" link to `/scalar` in the dashboard.
- **Browser tools for data** (dev-only resources with their own link in the dashboard, already connected): `postgres.WithPgWeb()` (pgweb: browse tables, run SQL), `cache.WithRedisInsight()` (browse cache keys) and `storage.AddBlobs("storage-blobs").WithAzureStorageExplorer()` (Community Toolkit package `CommunityToolkit.Aspire.Hosting.Azure.Extensions`; browse, download and delete blobs). `storage-blobs` is the default name, so `AddBlobs` returns the blob service that already holds `images` instead of adding another one; `AddBlobContainer` on a blob service is obsolete, so the container stays on `storage`. All three are declared after the API, and their configure callbacks pass their `PrimaryEndpoint` to it with `WithReference` (no `WaitFor`). The API's `AddDevToolHealthCheck("pgweb")`/`("storage-blobs-explorer")`/`("redisinsight")` (`Extensions/HealthCheckExtensions.cs`) registers an `HttpHealthCheck` (`HealthChecks/`, GET `/` through a named HttpClient with base address `https+http://<service>`, because Aspire serves RedisInsight over https with the dev certificate while pgweb and Storage Explorer stay on http) only when Aspire supplied a `services:<service>` URL, with failure status `Degraded`: a stopped tool turns the Admin amber, not red, and Aspire's `/health` still answers 200.

### Validation is duplicated on purpose; keep it in sync

Field rules live in several places. Changing one means changing all of them:
1. Domain entity `Create`/`Update`: required and positive checks only (no max lengths)
2. API request validator (FluentValidation, messages like `"Name is required"`): required, positive, max length, enums
3. EF entity configuration (`HasMaxLength`, `IsRequired`) plus a migration if the schema changes
4. Admin request class DataAnnotations (messages end with a period: `"Name is required."`): required, positive, max length

## Admin web conventions (`web/OrderPoint.Admin`)

### Structure

- Feature folders: `<Feature>/Api` (`<Feature>ApiClient`, `Requests/`, `Responses/`), `Components/`, `Dialogs/`, `Dtos/`, `Enumerations/`, `Pages/`, `Sorting/`. Cross-feature code is in `Shared/` (`Components/`, `Constants/`, `Extensions/`, `Layout/`, `Pages/`). Reusable formatting helpers are `internal static` extension methods in `Shared/Extensions/<Type>Extensions.cs` (e.g. `DateTimeOffset.ToRelativeTime()` → "2 h ago"), not private methods on a page.
- Code the bartender app needs too lives in the Razor class library `web/OrderPoint.Shared` (namespaces `OrderPoint.Shared.<Folder>`, same folder layout: `Account/` (all but `AccountPage`), `Auth/`, `Components/` (`StatefulView`, `ChipSkeleton`, `StatusMessage`, `SettingsSection`), `Constants/` (`ImageUrls`, `ImageStyles`, `DeclineReasons`), `Dtos/` (`PaginationDto`, `ImageFileDto`), `Errors/`, `Extensions/` (CultureInfo, DateTimeOffset, Int, ImageFileDto, OrderStatus), `Layout/` (`AppTheme`, `ReconnectModal`), `Orders/` (`OrderDto`, `OrderItemDto`, `OrderBartenderDto`, `OrderStatus`, `OrderAvatar`, `DeclineReasonField`; the rest of the feature stays in the Admin), `Items/` (`ItemCardContent`, `ItemCardImage`, `ItemCardContentSkeleton`), `Services/` (`ApiService`, `TimeZoneService`, `DarkModeService`), `wwwroot/images/` (logo, placeholder)). Admin-only helpers (e.g. `DashboardPeriodExtensions`) stay in the Admin's `Shared/`.
  - **Static files:** the library's `wwwroot` files and collocated JS are served under `_content/OrderPoint.Shared/` (e.g. `ImageUrls.Logo`); its scoped CSS reaches each app through the app's own `<App>.styles.css`.
  - **Visibility:** types stay `internal`; the apps see them through `<InternalsVisibleTo>` in `OrderPoint.Shared.csproj` (add each new web app there). Components stay `public`.
  - **Usings:** the Razor SDK has fewer implicit usings than the Web SDK, so files there add e.g. `Microsoft.Extensions.Logging` and `System.Net.Http.Json` themselves.
- Every component is split into `X.razor` (markup only) and `X.razor.cs` (`public sealed partial class X`). No `@code` blocks.
- Visibility: components are `public` (Razor requires it), so DTOs, enums and `PaginationDto` used as component parameters are `public`. Everything else (API clients, requests, responses, sort enums, `XSorting` helpers, services) is `internal`.
- Inject with `[Inject] private T Name { get; set; } = null!;`. Parameters use `[Parameter]` and `[EditorRequired]` where mandatory.
- Add new namespaces that pages use to `_Imports.razor`.

### API calls

- API clients are `internal sealed`, use relative URIs without a leading slash (`api/items?...`), escape user text with `Uri.EscapeDataString`, are typed HttpClients (`internal sealed class XApiClient(HttpClient httpClient)`), call `ApiExceptionHelpers.ThrowApiExceptionAsync` on non-success, and unwrap `.Data` from the response record. Register them in `Program.cs` with `builder.Services.AddHttpClient<XApiClient>(ConfigureApiClient).AddHttpMessageHandler<AccessTokenHandler>()` (base address in `ConfigureApiClient`; the handler attaches the access token). Only `AuthApiClient` is registered without the handler. Typed clients are transient, so never store one in a singleton.
- Pages and dialogs call API clients **only** through `ApiService`, which owns all API error handling and snackbars:
  - Queries: `T? result = await ApiService.ExecuteAsync(() => client.GetXAsync(...))`. Returns `null` on failure (error snackbar already shown), so fall back: `Items = Pagination?.Items ?? [];`.
  - Mutations: `bool isSuccess = await ApiService.ExecuteAsync(() => client.CreateXAsync(request), $"Item {request.Name} created successfully");`. Shows the success snackbar on success and the error snackbar on failure; reload the list only when `isSuccess`.
  - Autocomplete `SearchFunc`s pass MudBlazor's `CancellationToken` to both the client and `ExecuteAsync`, so cancelled searches are silent: `return categories ?? [];`.
  - Pages never inject `ISnackbar` for API results.
  - Snackbars stay 2 s in every app (`SnackbarVisibleMilliseconds` in each `Program.cs`; MudBlazor's default is 5 s).
  - `ApiService` logs unexpected exceptions (network, parsing); expected API errors (ProblemDetails), cancellations and `SessionExpiredException` are not logged.

### Pages and dialogs

- **Sections load independently and in parallel.** Each section of a page (a table, a highlight card, a list in a dialog) has its own `Get<Section>Async` method and its own `IsLoading<Section>` flag; the method ends with `StateHasChanged()` so the section renders as soon as its data arrives. `OnInitializedAsync` and post-mutation reloads start independent sections with `await Task.WhenAll(...)`; never await independent loads one after another. Only dependent steps stay sequential (mutation → reload).
- Highlight sections above a list (Categories: top 5 by item count; Items: spotlight cards for newest, last edited, highest and lowest price; Bartenders: team strip with active avatars, active/inactive balance and newest member; Orders: status pipeline of `OrderStatusCard`s, Pending → Accepted → Active → Completed plus Declined and Cancelled, where clicking a card filters the timeline and clicking it again clears the filter; the counts follow the bartender filter) reuse the list endpoint with `pageSize`/`sortBy`/filters (the pipeline makes one `pageSize: 1` call per status and reads `TotalCount`); they do not get their own endpoints.
- Dashboard (`Dashboard/Pages/DashboardPage`, route `/`): bento `MudGrid` (4 KPI cards; revenue trend area chart + busiest-times heat map + category donut on the left, tall "Right now" live panel on the right; top items, bartender leaderboard, recent orders below). Tiles use `DashboardTile` (icon, title, optional `HeaderContent`, `StatefulView`, optional `ContentHeight` that keeps loading/empty states as tall as the content; the revenue tile passes `RevenueTrendChart.ChartHeight` so the left column always matches the "Right now" panel) and `DashboardKpiCard` (value + ▲/▼ change chip vs previous period, `IsLowerBetter` for service time). A `MudToggleGroup` period switch in the `PageHeader` reloads the period sections; the live panel (open orders, longest wait, today so far: orders, completed, revenue, average order) refreshes every 30 s with a `PeriodicTimer` disposed with the page. Top items rows open `ItemDetailsDialog`, leaderboard rows open `BartenderOrdersDialog` (each fetches the full DTO first), recent orders open `OrderDetailsDialog`; all three lists highlight the hovered row with `var(--mud-palette-table-hover)`. All three charts are hand-built for a consistent hover experience (MudChart has no hover-anywhere crosshair and its tooltips are small): the revenue trend (SVG area + crosshair), the busiest-times heat map (HTML grid) and the top-5 category donut (SVG ring; hovering a segment or legend row shows the category in the centre). Revenue trend and heat map: transparent per-column slots set the hovered index and show a `MudTooltip` with `TooltipContent` (body2 label + h6 value), SVG coordinates are formatted with `CultureInfo.InvariantCulture`, colours come from palette CSS variables (`var(--mud-palette-primary)`, `rgba(var(--mud-palette-primary-rgb), …)`). In Razor loops, copy the loop variable into a local before using it inside child content or lambdas (`int rank = i + 1;`), otherwise every row renders the final value.
- List pages: `private const int PageSize` (10 for `DataTable`, `DataAccordion` and `DataTimeline`, 16 for the 4-column `DataGrid` (4 rows), 5 for `DataList` in a dialog); one `Get<Plural>Async(int pageNumber)` that reads the current search/sort/filter properties; search, sort and filter changes call it with `pageNumber: 1`; `OnPageChangedAsync(int pageNumber)`.
- Sorting is passed as the sort enum's name: `SelectedSortBy = nameof(ItemSortBy.CreatedAtUtcDesc)`; labels and icons come from `<Feature>Sorting.GetSortByLabel/GetSortByIcon`. Item dropdowns use `ItemSorting.SortByOptions` (name, price, created); `UpdatedAtUtcDesc` only feeds the "Last edited" spotlight. Category dropdowns use `CategorySorting.SortByOptions` (name, display order, created); `ItemsCountDesc` only feeds the top 5 cards.
- Create/update/delete/details are MudBlazor dialogs opened from the list page (not separate pages). Dialogs return the request object via `MudDialogInstance.Close(DialogResult.Ok(Request))`; the page performs the API call and reloads. Use early returns: `if (dialogResult.Canceled) { return; }`. Read-only features (Orders) only have a details dialog (whose only action is declining an open order).
- Delete dialogs take the DTO and show: an error alert "This action cannot be undone.", an outlined summary card (72px image or large `BartenderAvatar`, name with status chip, key facts, "Created … ago"), then "This also deletes:" with what goes with it (the image, a bartender's login). The confirm button reads "Delete <name>". The bartender card is `BartenderSummaryCard`, shared with the reset password dialog.
- Bulk actions:
  - **Selection:** `DataTable`, `DataGrid` and `DataAccordion` take `@bind-SelectedItems` (a `HashSet<TItem>`) and a `BulkActionsTemplate`. The checkboxes are always visible: MudTable's `MultiSelection` column with select-all, the top-left corner of grid cards, and the start of accordion headers (`stopPropagation`, so the panel doesn't toggle). Selected rows and cards get the `table-hover` background.
  - **Bulk bar:** while something is selected, `BulkActionBar` covers the toolbar row (same grid cell, toolbar hidden but still taking its space, so the list never moves) and shows "n selected", the page's actions, "Select all n" and "Clear". Selection is page-scoped: `Get<Plural>Async` clears it on every load.
  - **Actions:** Activate and Deactivate open `Change<Plural>StatusDialog`. Delete opens `Delete<Plural>Dialog`; it is disabled while the selection contains a record that can't be deleted, and its tooltip names those records.
  - **Dialogs:** both list the selection with `BulkSelectionSummary` (first 5, then "and n more") and say what happens or what else gets deleted.
  - **Messages:** counts in UI text use `int.ToCountText(singular, plural)` ("3 categories").
- Global search (`Search/` feature folder):
  - **Opening:** the `SearchTrigger` in the app bar, or Ctrl+K / ⌘K. `wwwroot/js/search.js` registers the shortcut and calls `MainLayout.OpenSearchFromShortcutAsync` through a `DotNetObjectReference`.
  - **Focus and keys:** `GlobalSearchDialog` sets `DefaultFocus="DefaultFocus.FirstChild"` on the `<MudDialog>` component itself. `MudDialog` wraps its content in a focus trap that reads this parameter, not `DialogOptions.DefaultFocus`, and otherwise moves focus from the field to the dialog element. ↑/↓/Enter use `MudDialog.OnKeyDown`, which the container's key interceptor fires for any key inside the dialog.
  - **Searching:** no backend of its own. It runs the existing list and search endpoints in parallel, 5 results per group: orders by number or table, items, categories and bartenders. Pages whose title contains the query are matched locally and listed first. Each group has its own loading flag and skeleton rows, and a new query cancels the previous one.
  - **Empty query:** shows "Recent" (the last 5 opened results, per browser in `ProtectedLocalStorage`) and "Pages".
  - **Keyboard:** ↑/↓ move the highlight, Enter opens, Esc closes. A `SearchResultRow` that becomes active scrolls itself into view after rendering (`scrollSearchResultIntoView`, `block: "nearest"`), so keyboard navigation follows long result lists.
  - **Opening a result:** the dialog returns a `SearchResultDto`, and `SearchService.OpenAsync` navigates to a page, or fetches the record fresh by id and shows the same details dialog the dashboard uses (bartenders open `BartenderOrdersDialog`).
  - **Items only:**
    - "Move" opens `ChangeItemsCategoryDialog`: a category autocomplete with images and the clear fix, plus a warning when the target category is inactive.
    - "Adjust price" opens `AdjustItemsPriceDialog`: mode, a value with a % or € suffix, and a live old → new preview. It uses `PriceAdjustmentMode.Apply` from `Shared/Extensions`, which mirrors the API's calculation. Confirm is disabled while the value is invalid or any new price would not be positive. `UpdateItemDialog` offers the same modes for one item (Price select + Value with the % or € suffix and "€4.50 → €4.95" as helper text; Set starts with the current price, the change modes start empty, meaning no change) and sends the resulting price; `CreateItemDialog` keeps a plain Price field with the € suffix.
    - Both dialogs return their request object, with the category name as `[JsonIgnore]` for the success message.
- A dialog that changes data the page shows (e.g. items inside `CategoryDetailsDialog`) exposes an `EventCallback On<Thing>Changed` parameter and invokes it after a successful mutation; the page passes `EventCallback.Factory.Create(this, ...)` in the `DialogParameters` and reloads. Do not rely on the dialog result for this: closing with X/Escape returns `Canceled`.
- Dialogs and components initialise state and load data in `OnInitialized`/`OnInitializedAsync` (parameters are already set). Do not use `OnParametersSet`: it runs again whenever the dialog provider re-renders, which resets forms and reloads lists. Exception: display-only chart components (`RevenueTrendChart`, `BusiestTimesHeatMap`, `CategoryRevenueDonut`) build their `ChartSeries`/labels from parameters in `OnParametersSet`, so charts are rebuilt only when their data changes, not on every render. `RollingNumber` and `StableHeight` also react to parameter changes there (a new value, loading starting).
- Forms: `EditForm` + `DataAnnotationsValidator`, MudBlazor inputs with `Variant.Outlined`, `HelperText`, `Immediate="true"`. Helper texts fit on one line at the field's width (about 40 characters for a half-width field in a Medium dialog). Fields side by side get `Class="flex-1"` plus `Style="min-width: 0"`, so a longer helper text can't make one wider than the other. `OnValidSubmit` only closes the dialog. Add `OnInvalidSubmit` + `IsFormSubmitted` only for inputs not covered by DataAnnotations `For` (e.g. a `MudAutocomplete` showing `Error`/`ErrorText`).
- Lookup autocompletes (category on Items, bartender on Orders): the API client's `Search<Plural>Async` returns the first 5 by name for empty text, else calls `api/<plural>/search`. Options use an `ItemTemplate` with a 24px picture next to the name (`MudImage` with `ObjectFit.Cover` and the placeholder for categories, `BartenderAvatar Size="Size.Small"` for bartenders); the input itself stays plain text. A `Clearable` autocomplete gets a `@ref` and `OnClearButtonClick` calling its `OpenMenuAsync()`, because MudBlazor 9 empties the list on clear without searching again ("No ... found" instead of the 5 defaults).

### Components and styling

- Each page has exactly one `<h1>`: the `PageHeader` title (rendered as `h1`, styled `Typo.h4`). `Routes.razor` focuses it after navigation, so nothing else (e.g. drawer labels) may render as `h1`.
- Reuse shared components: `PageHeader` (the page title, no breadcrumbs; optional `ChildContent` renders on the right of the title, e.g. the dashboard period switch), `DataTable` (tabular list, see Categories), `DataGrid` (card grid, see Items), `DataAccordion` (expandable rows with `HeaderTemplate`/`DetailsTemplate` and actions inside the expanded row; collapsed rows highlight on hover; a divider separates the details from the actions row; optional `ActionsTemplate` adds page-specific buttons before Edit/Delete, e.g. Reset password; see Bartenders, whose expanded row shows two balanced columns split by a vertical divider: ID, Phone, Notes on the left; Orders ("42 · last order 2 h ago", `BartenderOrdersSummary`, which loads the last order when the row expands because collapsed panels do not render their content), Created, Updated on the right; its Orders action button (before Reset password) opens `BartenderOrdersDialog`, the same dialog the dashboard leaderboard opens, with search, sort and paging), `DataTimeline` (read-only vertical timeline of clickable tickets with search and sort but no create/edit/delete; optional `FilterContent` like `DataGrid` (the Orders bartender filter); `GetItemColor`/`GetItemIcon` style each dot, `ItemTemplate` renders the ticket, `OnItemClick` opens details; tickets get the `table-hover` background on hover and the frame replaces the timeline's former top and bottom borders; see Orders), `DataList` (list inside a dialog, with dense search and sort; its `StableHeight` always keeps the height (`KeepHeight="true"`), so searching never shrinks the dialog; the create button only shows when `OnCreateClick` is set, so it also works read-only, see `ItemDetailsDialog`), `StatefulView` (loading/empty states for every independently loaded section; `Compact="true"` renders them without the surrounding paper, for use inside a card; both show the spinner with "Loading..." inside), `HighlightCard` (the shared card shell for highlight sections: centred label chip, `table-hover` background on hover, click, compact loading/empty state; optional `Height`, default 250, and `IsSelected`, which fills the chip and keeps the hover background, like a toggle; feature cards such as `TopCategoryCard`, `ItemSpotlightCard` and `OrderStatusCard` only supply the content), `TextDisplayRow` (label + `Text`, or `ChildContent` for richer values such as an avatar with name and email). Extend them rather than building parallel ones. The five list components keep their height: the rows and skeleton sit in `StableHeight` (a `min-height` set by `StableHeight.razor.js` when loading starts, kept while on page 2 or later, released once page 1 has rendered), and `ListPager` ("Showing x to y of n" + pager: `BoundaryCount="1"`, `MiddleCount="1"`, so `1 2 3 … 10`, `1 … 5 … 10`, `1 … 8 9 10`) sits below it and stays rendered, disabled, while loading, so turning pages never moves the pager. Choosing a page scrolls to the top first (`ListPager.razor.js`: the dialog content inside a dialog, else the window). Every list frames its rows with `StableHeight IsFramed="true"`: a subtle tint (`rgba(var(--mud-palette-text-primary-rgb), 0.02)`) and a `lines-default` border, so the held space reads as part of the list. `DataTable` and `DataAccordion` use it without padding as the list's own edge (their `MudTable`/`MudExpansionPanels` have `Elevation="0"`, so no second border; the tint continues below the rows); `DataGrid`, `DataTimeline` and `DataList` add `Class="pa-3"` around their cards, tickets and rows. Inside a frame `StatefulView` takes `Flat="true"`: the full-size loading and empty states without a paper of their own, centred in the held height (the frame is a flex column and they grow to fill it). `DataTable`/`DataGrid`/`DataAccordion` show the delete button when `OnDeleteClick` is set; `DeleteButtonDisabled` and `DeleteButtonDisabledTooltipText` are optional.
- Loading states are skeletons that mirror the real layout. Each layout has a `<Real>Skeleton` component next to the real one (`ItemCardContentSkeleton`, `OrderTicketSkeleton`, `CategoryRowSkeleton`, `RevenueTrendChartSkeleton`, ...), built from `MudSkeleton` (default wave) and the shared `ChipSkeleton`. Every placeholder line sits inside a `MudText` with the real `Typo`, so heights match, and static labels stay real text (e.g. the live panel's status names). List components take `LoadingTemplate` (one row/card) and repeat it inside their real containers, at most 3 rows (the item grid: 3 rows of 4 cards); skeleton lists elsewhere (dashboard lists, donut legend) also stop at 3, while charts, the heat map and rows of cards keep their real shape; `StatefulView`, `HighlightCard` and `DashboardTile` take `LoadingContent`. Without them the spinner remains. `App.razor` recolours the wave with the text colour so it shows in dark mode. Pages only pass the skeleton; no skeleton markup in pages or real components.
- Times are stored and sent as UTC. The Admin shows them in the browser's time zone: `TimeZoneService` (scoped, loaded once per circuit in `MainLayout` from `Intl.DateTimeFormat().resolvedOptions().timeZone`, UTC if unknown) and `dateTime.ToDisplayDateTime(TimeZoneService.TimeZone)` everywhere a date-time is displayed ("Today 14:30", "Yesterday 9:15", else the locale's short date and time, no seconds). For any other format convert with `ToTimeZone(...)` first; never call `ToString` on a `*AtUtc` value directly. `DashboardApiClient` sends `TimeZoneService.TimeZone.Id` as `timeZone`. Relative times (`ToRelativeTime`) need no conversion.
- Formatting follows the viewer's browser: `UseRequestLocalization` (all cultures, from `Accept-Language`) plus a middleware in `Program.cs` that swaps in `CultureInfo.ToDisplayCulture()` (`OrderPoint.Shared/Extensions/CultureInfoExtensions.cs`): the locale's number, date and 12/24 h formats, but English day and month names to match the UI, and amounts always in euros with 2 decimals. So format with `CultureInfo.CurrentCulture` (`"C"` for money, `"t"`/`"g"` and `GetShortMonthDayPattern()` for dates, `Uses12HourClock()` for hour-only labels), never hardcode `HH:mm` or `dd.MM`, and use `InvariantCulture` only for CSS/SVG numbers.
- Order status colours and icons come from `OrderStatus.GetColor()`/`GetIcon()` in `OrderPoint.Shared/Extensions/OrderStatusExtensions.cs`; use them everywhere a status is shown (pipeline, timeline dots, chips, details timeline).
- Admin DTOs, enums and sort enums mirror the API ones by hand. When an API contract changes, update the Admin copy too.
- Use MudBlazor components and `Icons.Material.Filled.*`; avoid custom CSS. Colours come from the theme in `OrderPoint.Shared/Layout/AppTheme.cs`, never hardcoded hex. The theme is tweakcn's "vercel" (monochrome dark and light palettes: primary is black in light mode and white in dark mode, so `PrimaryContrastText` is set per palette; Geist font, 8px radius, no shadows in either mode (every theme elevation is `none`, and the global `<style>` block in `App.razor` also removes the filled-button shadow), buttons not uppercase; every elevated surface gets a `lines-default` border from that same `<style>` block, so use `Elevation="0"` for a surface that must stay borderless (always on `MudTimelineItem`: the border would squash its filled dot into an oval; its `Icon` parameter is ignored in MudBlazor 9.6, so put a small `MudIcon` in `ItemDot`); hover is a background change, never a lift); the app bar and drawer are separated by `lines-default` borders, not elevation. Dark mode and an open drawer are the defaults; both are remembered per browser in `ProtectedLocalStorage`. Dark mode lives in the scoped `DarkModeService` (`OrderPoint.Shared/Services`): `MainLayout` applies it and re-renders on `Changed`, and the account page's Appearance section changes it (there is no app bar toggle). Elsewhere: dialogs use `Class="mud-background"`, borders use `var(--mud-palette-lines-default)`.
- Razor attribute style:
  - Plain for literals, enum values and type parameters: `Label="Sort by"`, `Clearable="true"`, `Variant="Variant.Outlined"`, `T="string"`, `TItem="ItemDto"`.
  - `@` for anything that references code, including directive attributes: `Items="@Items"`, `OnClick="@Cancel"`, `@bind-Value="@Request.Name"`, `Icon="@Icons.Material.Filled.Add"`.
  - `@(...)` for lambdas and expressions: `OnClick="@(() => ShowDeleteItemDialogAsync(item.Id, item.Name))"`.
- The mockups in `design/` are inspiration only; the owner decides layout and fields per screen. Do not add fields or screens from a mockup unless asked.

## Bartender app conventions (`web/OrderPoint.Bartender`)

Same structure and rules as the Admin (feature folders, `X.razor` + `X.razor.cs`, typed API clients called through `ApiService`, skeletons, live reloads), but built for phones and tablets.

- **Shell:** `Shared/Layout/MainLayout`: a dense app bar (logo, "OrderPoint / Bartender web", `LiveIndicator` showing the `OrdersHubService` state: green Live, amber Connecting, red Offline) and `BottomNavigation`, fixed to the bottom (Orders `/`, which also matches `/orders/...`, My shift `/shift`, Menu `/menu`, Account `/account`); `MainContent` is padded by its height. Snackbars sit at the top. Pages have one `h1` (`Typo.h6`/`h5`, no `PageHeader`). Empty states use a short title plus `StatefulView.EmptyStateDetail` for the hint on a second line ("Nothing in progress" / "Accept an order from the queue."). Dialogs are only for confirmations (sign out, sign out everywhere); anything else (details, forms) is its own page with a back arrow before the h1 (`MudIconButton` with `Href` to the parent page), e.g. `OrderDetailsPage`, `DeclineOrderPage`, `MenuItemPage`, `ChangePasswordPage`. Search fields use `Placeholder`, not `Label`, so the text sits inside the field next to the search icon.
- **Orders (`/`):** Queue / Mine / Done tabs (`OrdersTab`; the scoped `OrdersTabState` remembers the last one for the session, and on a tablet the order open in the panel (`SelectedOrderId`), so coming back from My shift, Account or an order opens it again; the tab bar sticks under the dense app bar while scrolling (a wrapper in the page background, `top: 48px`), and it is a paper like the tickets (border, theme radius, `overflow: hidden`) holding a row of three `flex-1` text buttons with a 2px primary underline on the selected one, not `MudTabs`, whose tab bar only grows as wide as its tabs; the selected tab's list renders below), each an `OrderTicketList` of `OrderTicket`s (number tile, table, "Placed 3 min ago" or "Completed Today 14:30", total, status chip, one line per item, note). On an open order (Pending, Accepted, Active) the placed time turns amber (warning, semibold) from 5 minutes and red (error) from 10, so the longest waits stand out. Queue: every Pending order, oldest first (new ones highlighted with `NewOrdersTracker`). Mine: my Active, then my Accepted orders. Done: my Completed and Declined orders finished since the day start (`TimeZoneInfo.GetTodayStartUtc(Configuration.GetBusinessDayStart())`, `Shared/Extensions/ConfigurationExtensions`), newest first. Each status is one `GET api/orders` call of up to 50 (`bartenderId` = `AuthService.UserId`), no paging. Tab counts are `TabCount` pills with `RollingNumber`. Every tab reloads silently on `OrdersChanged`, and a 30 s timer re-renders so relative times move on. A search field ("Order number or table", dense, in the same sticky header above the tabs) uses `GET api/orders?searchQuery=`: while it has text the tab bar is hidden and the list shows matching orders of any status and any bartender, newest first, 20 at a time with "Show more" and an "n orders found" caption; the tickets add who handles them (`OrderTicket.ShowsBartender`: "· Ana Horvat" or "· you"). A result opens like a tab ticket (phone page or tablet panel); `OrdersChanged` reloads as many results as are shown (whole pages, at most 100), and a response for an older search text is ignored. Clearing the field brings the tabs back.
- **Order details:** `OrderDetails` loads the order by id, follows it live (`OrdersChanged`; a failed reload keeps what is shown) and shows the header (number tile, table, placed, status), one row per item (40px image, "**2×** name", line total), the note, the total, the status steps with times, and who handles it ("Handled by you"). Its action bar (big buttons, always at the bottom: on a phone fixed to the screen above the bottom navigation, with room left under the details; in the tablet panel, which is as tall as the screen allows, below the details that scroll inside it) matches what this bartender may do: Pending → Decline + Accept (any bartender), Accepted and mine → Decline + Start, Active and mine → Complete; other bartenders' orders have no buttons. Decline opens `DeclineOrderPage` (`/orders/{id}/decline`: back arrow, the order's `OrderTicket`, a warning, the shared `DeclineReasonField`, and a large "Decline order" button with a spinner, disabled while the reason is empty or the order can no longer be declined by this bartender; a refusal reloads the ticket, success goes to `/`; the back arrow returns to the tablet panel when `OrdersTabState.SelectedOrderId` is this order, else to `/orders/{id}`), and a declined order shows its reason under the status steps. While the API answers, the tapped button shows a spinner and every button is disabled (`WorkingAction`, an `OrderAction`). After Accept or Start it stays and reloads; after Complete it raises `OnFinished`; a refused change (409, e.g. accepted by someone else first) shows the API's message and reloads. The actions go through `OrderApiClient.Accept/Decline/Activate/CompleteOrderAsync` (`PUT api/orders/{id}/<action>`, no body).
- **Phone vs tablet:** `OrdersPage` subscribes to `IBrowserViewportService`; below 600 px (`Breakpoint.Xs`) a ticket opens `/orders/{id}` (`OrderDetailsPage`: back arrow, `OrderDetails`, its buttons sticky above the bottom navigation; `OnFinished` goes back to `/`), from 600 px the page splits: the list (5/12) and a sticky details panel (7/12) with the selected order (`OrderDetails IsInPanel="true"`, keyed by id; `OnFinished` and `OnClose` (the × after the status chip, shown only when `OnClose` is set) clear the selection; the selected ticket gets the `table-hover` background and a primary border) or a "Select an order" prompt.

The three order tiles set `OrdersTabState` and open the Orders page on that tab. Below them "My day" (h2) loads `GET api/shift/day` in parallel (own loading flag, `ShiftDaySkeleton`, empty state "Nothing served yet"): `ShiftDay` shows Served (€) and Items served, `ShiftHoursChart` (hand-built HTML bars, counts above the bars because phones have no hover, hour labels every 1/2/3 hours depending on the shift's length, locale 12/24 h) on the left (7/12 from 600 px) and "Most served" (the Admin's top items row look: 40px image, "9×", share bar, revenue) on the right (5/12).
- **Menu (`/menu`):** to answer guests, and to take things off the menu when they run out (`Menu/`: `MenuApiClient` over `GET api/categories` (up to 100, `DisplayOrderAsc`), `GET api/categories/{id}` and `GET api/items` (one category, `NameAsc`, 20 per page), with its own copies of the item and category DTOs, enums and sort enums). `MenuPage` is a grid of `MenuCategoryCard`s in menu order (centred 56px thumbnail, greyscale when inactive; the name below it, up to 2 lines; an Active/Inactive chip below that; 3 per row on a phone, 4 from 600 px, 6 from 960 px) with a sticky search (debounced, category name). Unavailable items (`ItemDto.IsActive`, same rule as the Admin) stay listed with a greyscale picture and an "Unavailable" chip. A row opens `MenuItemPage` (`/menu/{categoryId}/items/{id}`, loads `GET api/items/{id}`, back arrow to the category; `MenuItemDetails`: a warning saying why an unavailable item can't be ordered, then the Admin's item card (`ItemCardContent` with the whole description)). The item page has an "Available to guests" switch in a paper above the details ("Turn off when it runs out."; the item's own status), and the category page a switch after the name in its header (labelled Active or Inactive) instead of the status chip. Both apply at once through the bulk status endpoints with one id (`MenuApiClient.ChangeItemsStatusAsync`/`ChangeCategoriesStatusAsync`, requests in `Menu/Api/Requests`), show a snackbar ("Mojito deactivated", no confirmation, since it is easy to undo), and reload what they show; the category page updates its loaded items' category status in place, so "Show more" pages stay. The three pages follow `OrdersHubService.MenuChanged` live without skeletons (a failed reload keeps what is shown; the category page reloads every page shown so far, so "Show more" stays).
- **Account (`/account`):** a profile card (photo the admin set or the name's initials, full name, email and phone number with icons, Bartender chip, "Your name, email, phone number and photo are set by the admin.", all from `AccountService`) and a settings card of the shared `SettingsSection`s (icon, title, description, the control below at full width): Appearance (Light | Dark, `DarkModeService`), Password (`ChangePasswordPage` at `/account/password`: the shared dialog's fields and `ChangePasswordRequest` on a page, returns to `/account` after saving), Sessions (`SignOutEverywhereDialog`), Sign out (`SignOutDialog`).

## Customer app conventions (`web/OrderPoint.Customer`)

Same structure and rules as the bartender app (feature folders, `X.razor` + `X.razor.cs`, typed API clients through `ApiService`, skeletons, pages with a back arrow instead of dialogs except for confirmations, search fields with `Placeholder`), but for guests: no sign-in, no `AuthService`/`AccessTokenHandler`, every API call anonymous.

- **Shell:** `Shared/Layout/MainLayout`: a dense app bar (logo, "OrderPoint", a medium outlined "Table T7" chip with `px-3` once the table is known) and `BottomNavigation` (Menu `/`, which also matches `/menu/...`, Cart `/cart`, My orders `/orders`, Settings `/settings`); content in a `MaxWidth.Small` container. It renders nothing until `TableService` has loaded. Light or dark comes from `Settings/Services/AppearanceService` (scoped, `ProtectedLocalStorage`): `AppearanceMode` Auto (the default) follows the phone (`MudThemeProvider.GetSystemDarkModeAsync` + `WatchSystemDarkModeAsync`), Light and Dark override it.
- **Table:** a table's QR code opens `/t/{tableCode}` (`Tables/Pages/TablePage`), which stores the code (trimmed, in capitals, only letters, digits and hyphens, at most 10 characters like the API; anything else keeps the table the guest had) in `TableService` (scoped, `ProtectedLocalStorage` as `TableVisitDto(TableCode, ScannedAtUtc)`, raises `Changed`) and replaces the URL with `/`. A table is remembered for one visit (`Shared/Constants/Visit.Length`, 12 hours, shared with the cart and My orders), so a guest coming back days later scans again instead of ordering to an old table. Orders are sent with that `TableCode`.
- **Menu:** `Menu/Services/MenuService` (scoped) loads `GET api/menu` once (`MenuApiClient`, no token; a failed load is retried by the next page) and every menu page reads it; `MenuChanged` on the tracking connection (also raised after a reconnect) drops it and raises `MenuService.Changed`, and `MenuPage`, `MenuCategoryPage`, `MenuItemPage` and `CartPage` read it again (a failed reload keeps what is shown), so a deactivated item disappears, its page says it is gone, a cart line says "No longer on the menu" and prices follow, so searching filters locally as the guest types (`Immediate`, 300 ms debounce, name contains, ignoring case). `MenuPage` (`/`): h1, "Table T7 · What would you like?", a sticky category search, and `MenuCategoryCard`s in menu order (centred 64px thumbnail, name up to 2 lines, "n items"; 2 per row, 3 from 600 px). `MenuCategoryPage` (`/menu/{id}`, back arrow to `/`): picture and name, the category description, a sticky item search, and `MenuItemRow`s (56px picture, then name, price and "Portion 0.3 · description" on three lines, and the cart control described under Cart). `MenuItemPage` (`/menu/{categoryId}/items/{id}`, back arrow to the category): the shared `ItemCardContent` without status and orders count, whole description. A category or item that is no longer on the menu shows "... not found / It may have been taken off the menu."
- **Cart:** `Cart/Services/CartService` (scoped, loaded by `MainLayout`, saved in `ProtectedLocalStorage` on every change, raises `Changed`) keeps `CartLineDto(ItemId, CategoryId, Name, Quantity)` lines (at most `MaxQuantity` 20 each) and the note, saved as one `CartDto` with the time of the last change and forgotten one visit (12 hours) after it; prices and pictures always come from the current menu, the name only labels a line whose item left the menu. Item rows (name, price, "Portion 0.3 · description") end with a filled + button, and once the item is in the cart with a `QuantityStepper` (− n +; with `Min="0"` the minus becomes a bin at 1), inside a `stopPropagation` wrapper so the row doesn't open. The item page (card without portion) has a stepper and "Add · €18.00" until the item is in the cart, then "In your cart" with a `Min="0"` stepper and "View cart". Adding or removing shows no snackbar: the + turning into − n + (or the item page into "In your cart") is the feedback. The Cart tab shows a badge with the number of pieces to the right of the icon (`Origin.CenterRight`), so it fits inside the button and the bar stays exactly like the bartender app's (64px, same buttons and ripple); My orders shows one the same way with the number of open orders. Right above the navigation, `Shared/Layout/OrderStatusBar` (48px, fixed, same surface and top border; `MainLayout` adds its height to the content padding while it shows) links to the guest's latest order: status icon in its colour, "**Order #128** · Being prepared" (a declined order adds its reason; one line with an ellipsis), a "+1" chip when other orders are open (it then links to My orders), and a chevron. It shows the newest open order, else one that finished in the last 10 minutes (`MyOrdersStatusService.LatestOrder`), and is hidden on My orders and the order pages, which show the same in full.
- **Placing an order (`/cart`):** a "Clear" text button next to the h1 while the cart has lines (empties the lines and the note, no confirmation), a warning without a table, `CartLineRow`s (picture, name, "€8.00 each · €16.00", stepper; "No longer on the menu" and a bin for a line whose item is gone), a note (`Label` "Note for the bartender", 200 characters with counter like the API, `Immediate` so the counter follows the typing), the total and "Place order" (disabled without a table, with lines that left the menu, or while sending; spinner). `POST api/orders` goes through `Orders/Api/OrderApiClient` and returns the shared `OrderDto`; on `Order.ItemIsUnavailable` or `Item.NotFound` the page calls `MenuService.Reset()`, reloads the menu so the gone lines are marked, and rethrows for `ApiService`'s message. On success (`ApiService.ExecuteAsync<OrderDto>`, no snackbar) the order is remembered in `MyOrdersService` and tracked, the cart is cleared, and the app opens the order's status page.
- **Following orders:** `Orders/Services/MyOrdersService` (scoped, `ProtectedLocalStorage`, raises `Changed`) keeps `MyOrderDto(Id, PlacedAtUtc)` for the orders placed on this phone; entries older than one visit (`Visit.Length`) are dropped on load. `Orders/Services/OrderTrackingHubService` (scoped, the staff `OrdersHubService`'s pattern without a token) connects to `<api>/hubs/order-tracking`, calls `TrackOrder` for every id it was given (again after each reconnect) and raises `OrdersChanged` on `OrderChanged` and after a reconnect. `MainLayout` loads my orders, tracks them and starts the connection (not awaited). `Orders/Services/MyOrdersStatusService` (scoped, loaded by `MainLayout`, not awaited) fetches them all (one tracking call per order in parallel), reloads on `OrdersChanged` and `MyOrdersService.Changed` (an older reload that answers last is ignored) and raises `Changed`; My orders, the My orders badge (`OpenCount`: Pending, Accepted, Active) and the status bar all read it. `OrderApiClient.GetOrderTrackingAsync` returns null for `Order.NotFound`, so a list of old ids shows no errors.
- **Order status (`/orders/{id}`):** back arrow to `/orders`, h1 "Order #128"; `OrderTrackingDetails`: a hero with the status icon (`OrderStatus.GetIcon/GetColor`) and the guest's wording (`Shared/Extensions/GuestOrderStatusExtensions`: `GetGuestTitle` "Sent to the bar", "Accepted", "Being prepared", "Served", "Declined", "Cancelled", and `GetGuestText`), the decline reason ("Reason: Out of stock"), and while the order is Pending a small text "Cancel order" button (`OnCancelClick`: `OrderPage` asks in `Orders/Dialogs/CancelOrderDialog`, "Keep order" or "Cancel order", calls `PUT api/orders/{id}/cancel` and reloads; once a bartender took the order the API refuses with 409 and the reload shows why), the status steps with times (like the bartender app's), the table, the lines (40px picture, "**2×** name", line total), the note and the total. It tracks the order itself too (so a shared link works) and reloads on `OrdersChanged`; a failed reload keeps what is shown.
- **My orders (`/orders`):** "Placed on this phone in the last 12 hours.", one `MyOrderCard` per order, newest first (`OrderAvatar`, table, placed time, total, status chip in the guest's wording, "2× Mojito, 1× Lager", an "Order again" button inside a `stopPropagation` wrapper, with an outlined "Cancel" button before it while the order is Pending, which asks in `CancelOrderDialog` like the status page), read from `MyOrdersStatusService` (skeletons until it has loaded, re-rendered on its `Changed`; a cancel asks it to reload). "Order again" adds the lines that are still on the menu to the cart (today's prices) and opens it; a warning snackbar says when some or all lines left the menu.
- **Settings (`/settings`):** one paper of `SettingsSection`s: Appearance (Auto | Light | Dark toggle group), Your table (the table, or "No table yet: scan the QR code on your table.") and Your orders ("Forget this phone's orders", which only clears `MyOrdersService`).

## C# style

- File-scoped namespaces matching the folder path; `using` directives at the top, outside the namespace.
- Classes are `sealed` by default and as little visible as possible (see Ground rules).
- Primary constructors for DI (handlers, repositories, API clients, exception handlers, services).
- Explicit types for locals (`Result<ItemDto> result = ...`, `Item? item = ...`, `string requestUri = ...`, `int i`). `var` only when the type is obvious from the right side: `new`, casts, mapper calls (`ToXDto()`), and generic calls naming the type (`GetRequiredService<T>()`, `Enum.Parse<T>()`). Never `var` for built-in types.
- Always braces, `is null` / `is not null`, collection expressions `[]`.
- Async methods end in `Async` and take a `CancellationToken`.
- Lines are at most 120 characters. When a call does not fit, break its arguments one per line; short calls stay on one line.
- Formatting follows `app/.editorconfig`: 4 spaces, UTF-8 **with BOM** for `.cs`, `.razor` and `.csproj` files, no final newline. Line endings are handled by git (`.gitattributes`: LF in the repo, CRLF in the working tree); keep CRLF when creating or editing files.

## Adding a new entity end-to-end (checklist)

Domain entity + errors (+ sort enum) → repository interface → EF config + EF repository + DbSet + registration → migration → DTO + mapper → commands/queries (cached reads with `CacheKeys`/`CacheTags`, writes implementing `ICacheInvalidatingCommand`, see Caching) → endpoints with validators and `RequireAuthorization(AuthorizationPolicies.Admin)` → Admin DTOs/enums/sorting → API client + requests/responses + registration → page + dialogs → nav link in `Shared/Layout/MainLayout.razor` (add it, or check it already exists; Orders and Bartenders already have links) → `dotnet build app/OrderPoint.slnx -c Release`.
