# Architecture decisions

The choices that shaped OrderPoint, each with its reason and its cost. Status is **Accepted** unless noted.

## ADR-01: Blazor Server for every app

- **Context:** five apps for very different users (guests on phones, staff on phones and tablets, a till, the owner's desktop), built by one developer in C#.
- **Decision:** every app is a Blazor Web App with the Interactive Server render mode and MudBlazor.
- **Why:** one language and one set of DTOs everywhere; tokens stay on the server; live updates are a server-side event that re-renders the circuit; shared components in one Razor class library.
- **Cost:** every open tab holds a connection to its app, a lost connection needs the reconnect dialog, and phones depend on a steady network. Fine for a bar's Wi-Fi.

## ADR-02: The apps call the API from their servers

- **Decision:** browsers only talk to their app; the app's server calls the API over HTTP with the user's bearer token and listens to the hubs with the SignalR .NET client.
- **Why:** no CORS, no tokens in browser JavaScript, one place (`ApiService`) for error handling, and phones need only the apps exposed through the tunnel.
- **Cost:** an extra hop per call, and images need the apps' `/images` proxy (ADR-13).

## ADR-03: Clean architecture with CQRS and the Result pattern

- **Decision:** Domain, Application, Infrastructure and Api projects pointing inwards; one file per use case (command or query plus handler) through MediatR; business failures returned as `Result` with coded errors, never thrown.
- **Why:** rules live in one place (the entities), use cases are easy to find, cross-cutting concerns (telemetry, caching, notifications) are pipeline behaviours, and error codes are stable for the apps.
- **Cost:** more files per feature, and the MediatR 14 license key.

## ADR-04: Minimal API, one endpoint per file

- **Decision:** each endpoint is a small class with its request record and validator in the same file, discovered automatically, documented with OpenAPI and shown in Scalar.
- **Why:** everything about an endpoint is in one place, and the documentation is generated from the code.

## ADR-05: PostgreSQL with EF Core, restrictive foreign keys, app-generated ids

- **Decision:** one PostgreSQL database through EF Core migrations applied at startup. Every foreign key is `RESTRICT` (except a stock count's lines); handlers check blockers first and return a clear conflict. Ids are `Guid.CreateVersion7()`; only the order number is generated by the database.
- **Why:** nothing disappears by accident, errors say why ("category with items"), time-ordered ids index well, and order numbers are readable.

## ADR-06: HybridCache with tags, Redis that may fail

- **Decision:** reads are cached in memory and Redis through HybridCache, cleared by tag when commands succeed. Redis calls fail fast while it is down.
- **Why:** cheap reads for the lists every app reloads on live updates, correctness through tag invalidation, and Redis as an optional speed-up rather than a dependency.
- **Cost:** every new command must declare what it invalidates.

## ADR-07: Live messages without data

- **Decision:** SignalR messages say only that something changed (`OrdersChanged`, `MenuChanged`, `TablesChanged`, `OrderChanged`); apps reload through the API.
- **Why:** one source of truth (the API with its rules and cache), no duplicated payloads to keep in sync, and lost messages are healed by reloading after a reconnect.
- **Cost:** a burst of changes causes several reloads.

## ADR-08: Identity's user store with JWT and rotating refresh tokens

- **Decision:** ASP.NET Core Identity only for users (hashing, lockout); short-lived JWT access tokens (15 min) and refresh tokens (7 days, stored hashed, replaced on use). Each app signs in with its own role.
- **Why:** standard, well-tested password handling without cookies or Identity UI; tokens suit server-to-server calls; revoking refresh tokens signs people out everywhere.
- **Cost:** a deactivated user's access token stays valid up to 15 minutes, so order actions re-check the bartender.

## ADR-09: Order lines keep their own copy

- **Decision:** an order line stores the item's name, picture and price when the order is placed; totals are calculated, not stored.
- **Why:** renaming, repricing or re-picturing an item never rewrites past orders, receipts or revenue.
- **Cost:** an item's old picture stays in storage while a line shows it.

## ADR-10: One payment per order, stored on the order; simulated cards

- **Decision:** payment status, method, times, who took it and cash received are columns on the order; the guest's card goes through `IPaymentProvider`, implemented by a simulator; the register only records card payments made on the bar's terminal.
- **Why:** a bar order is paid once and in full; no separate payment entity is needed. Real payment processing is out of scope.
- **Cost:** split bills and partial payments aren't possible.

## ADR-11: Stock leaves on completion, sold out is computed

- **Decision:** completing an order takes its recipes off the stock (never refusing); an item is sold out while an ingredient has less than one serving, computed rather than stored as a status.
- **Why:** completed means served, so stock follows reality; a computed status can't get out of sync, and items come back on their own when stock does.
- **Cost:** availability needs the recipe and stock loaded wherever an item is checked.

## ADR-12: A business day that starts at 06:00

- **Decision:** "today" on the dashboard, My shift, the register and the Done tab starts at a configured hour (6), in the viewer's time zone.
- **Why:** a bar's night runs past midnight and belongs to one day.

## ADR-13: Images served through the apps

- **Decision:** the API stores full blob URLs; each app rewrites them to its own `/images/...` path and streams the blob from storage with long cache headers.
- **Why:** phones can't reach the storage emulator, and only the apps are exposed through the tunnel. The API and stored data stay unchanged.

## ADR-14: Aspire for local orchestration, no deployment

- **Decision:** one `aspire run` starts the containers, the API, the five apps, the developer tools and (on demand) the tunnel. Nothing is deployed.
- **Why:** a full system with tracing, health and data browsers on one machine, configured in code. Deployment is out of scope.

## ADR-15: Validation in four layers

- **Decision:** rules are checked in the domain, the API validators, the database and the apps' forms, and kept in sync by hand.
- **Why:** each layer protects itself: forms help the user, validators give clear 400s, entities keep the rules true, the database is the last guard.
- **Cost:** a changed rule touches four places. See [Validation rules](Validation-Rules).

## ADR-16: Toward a modular monolith *(Proposed)*

- **Context:** the API's features are tangled through shared entities, repositories and cache tags.
- **Decision:**
  - Split the API into modules (Staff, Catalog, Floor, Inventory, Ordering, Reporting).
  - Each module owns its schema and DbContext and offers public contracts.
  - In-process events, in the same transaction, carry changes between modules.
  - Reporting works through the contracts.
- **Why:** clear ownership and boundaries the compiler enforces, while keeping one deployable application.
- **Plan:** [`docs/modular-monolith-plan.md`](https://github.com/mucnjakf/OrderPoint/blob/main/docs/modular-monolith-plan.md); see also the [Roadmap](Roadmap).
